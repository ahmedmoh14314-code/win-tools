# Reference implementations — architecture decision support (Phase 1B)

- **Date:** 2026-10-20. **Status:** research input for ADR-0001/0003/0004/0005/0006/0007, not a decision.
- **Sources:** our Spike 001 evidence (`2026-10-19-interaction-spike.md`), official Microsoft documentation (cited in the per-reference files), and the reviews in `references/`. Licenses and reuse status: [`references/README.md`](references/README.md).
- **Rule applied:** a pattern is adopted only after answering the six anti-copy questions (§3). "A successful project does it" is never the reason.

## 2. Lessons learned from mature projects (failure modes we design out)
1. **Code inside Explorer is fragile** (FileConverter: 43 shell-extension issues — missing menus on Windows 11, extension disabled, CLR injected into third-party processes crashing them #783, 10 s–1 min menu lag). Our drag→trigger→overlay design runs no code in Explorer. Keep it that way; if a context-menu entry is ever added, it must be a sparse-package `IExplorerCommand`, decided by ADR.
2. **In-process native engines kill the app** (#790). Engines only in the worker.
3. **Redirected-pipe deadlock**: reading one pipe while the child blocks writing the other (#700, #749, #780, #803). Always drain stdout and stderr asynchronously with a cap.
4. **Success inferred from text** broke files named "…Error…" (#247). Exit code + output validation only.
5. **Final-name writes and pre-emptive renames** violate originals-never-destroyed. Temp + validate + exclusive create.
6. **Extension = type** caused wrong engine choices. Content sniffing.
7. **Batch transport via argv** hit length limits and a second code path diverged (#614). We get paths via `CF_HDROP`; one IPC channel to the worker.
8. **One bad file aborted the batch** (#542); **modal error boxes from background code** blocked queues (#473).
9. **Colour/transparency (17 issues) and EXIF/orientation (7 issues)** are where users judge image conversion. V1 needs an explicit, tested policy: alpha flattening colour for JPEG, ICC handling, EXIF orientation applied or preserved, timestamps.
10. **Installer executing product code elevated** (#382) and per-machine installs writing per-user state (44 issues). Per-user, no elevation.
11. **Unsigned auto-update from a Git branch**; SmartScreen/Defender friction even for a signed OSS build (#302 expired certificate, #383 Defender flag). No updater in V1; plan for reputation friction.
12. **Hooks die silently** (rovyl #3, AutoHotPie #39, PowerToys #37380/#40423/#50678; #38089 root-caused to a swallowed key-up). Liveness probe + re-install on known events.
13. **Hidden overlays leak into screen shares** and **stale overlays block clicks** (AutoHotPie #115, #136). Hide means `SW_HIDE`, and the watchdog hides a shown overlay that never got DragEnter.
14. **Undocumented framework behaviour accumulates** (Action Wheel's six-step WinUI transparency, style ordering, double `Move`, black close flash). Prefer stacks where the overlay needs no reverse engineering.

## 5. Framework comparison (ADR-0001 input)
| Criterion | WPF + targeted interop | WinUI 3 + interop | Raw Win32 overlay + higher-level UI elsewhere | Hybrid: resident Win32 overlay host + on-demand WPF UI process |
|---|---|---|---|---|
| Idle memory (measured, Release) | 137 MB WS / 88.6 MB private | Not measured; expected ≥ WPF (GPU composition; Gradial 157 MiB) | 45.7 / 14.3 with GDI; production rendering (anti-aliased icons, text) **not measured** | Resident ≈ Win32 numbers; WPF cost only while settings/results are open |
| Overlay latency | 6–7 ms shown, DragEnter delayed by transparent dead zone (fixable, unverified) | Unknown; window-per-open pattern in the reference | 9–10 ms shown, DragEnter 10–20 ms | Same as Win32 |
| Transparent-window reliability | `AllowsTransparency` documented; alpha-0 fall-through must be avoided | No public API; 6 undocumented steps; open bugs #8594, #11172, #9990, #10119 | Window region or `UpdateLayeredWindow`, documented | Same as Win32 |
| DPI / multi-monitor | PMv2 supported; untested here | Supported; reference needed DPI re-read | Manual, small amount of code (done in spike); untested here | Mixed |
| Animation | Built in | Built in (composition) | Manual (Direct2D/DirectComposition needed for smooth effects) | Overlay manual, UI built in |
| Accessibility | UIA built in | UIA built in | Manual UIA provider for the overlay | Overlay manual; settings built in |
| Development complexity | Lowest | High (workarounds) | High for rich rendering | Highest (two UI stacks, IPC) |
| Packaging | Framework-dependent .NET desktop runtime | WASDK runtime or 250–300 MB self-contained | .NET runtime only | Two executables |
| Long-term compatibility | Mature, in maintenance mode | Active, but overlay scenarios are unsupported paths | Win32 is the most stable surface | Same |

**Status: undecided between "WPF for everything" and the Win32-overlay hybrid; WinUI 3 rejected for the overlay in V1.** The deciding unknown is the idle cost of a *production-quality* Win32 overlay (anti-aliased icons and text) versus WPF with a hit-testable dead zone. The 40 MB private-bytes budget is a hypothesis, not a requirement; if the owner accepts ≈ 90 MB resident, WPF wins on every other row.

**Smallest experiment that settles it (Spike 002, ≤ 1 day):** in the existing spike, (a) WPF host with the dead zone painted at alpha ≥ 1 → measure DragEnter without movement and drop fall-through on a transparent pixel with Explorer underneath; (b) Win32 host rendering the same ring with Direct2D into a 32-bit DIB shown with `UpdateLayeredWindow` (icons + text, anti-aliased) → measure idle private bytes, first paint, DragEnter; (c) cold start of both in Release. Pass bars: DragEnter ≤ 30 ms without movement, no fall-through, and an **owner-set idle private-bytes ceiling decided before the run** (e.g. 40 MB or 100 MB). If the ceiling is ≥ WPF's measured 89 MB, only part (a) is needed and the hybrid is dropped (ADR-0001 says a hybrid is evaluated only if a pure option fails a hard requirement). Part (b) needs Direct2D/DirectWrite interop and is more than a day.

## 6. Hook / input recommendation (ADR-0003/0005 input)
1. **Baseline: `WH_KEYBOARD_LL` + `WH_MOUSE_LL` on a dedicated thread.** It is the only mechanism verified end to end with Explorer and shell drags. It is **not yet the decision**: the 1000-cycle run (one gen0 GC, 1.8 ms) was a near-idle spike host with injected input at a low event rate, and callback time was measured inside the managed callback, so a GC-blocked *entry* is invisible to it; the timeout default is undocumented (1000 ms is only the cap). Decide in ADR-0005 after E1 (entry latency under GC churn, in the chosen UI stack) and E2 (Raw Input during an Explorer drag); the research recommendation in `references/input-hook-robustness.md` §5 (Raw Input always-on, LL hook only per session) remains the leading alternative.
2. Harden it: allocation-free callbacks, no I/O, `try/catch` in the proc, all-or-nothing install, mouse **and** keyboard liveness probes, re-install on unlock/resume/display change/Explorer restart, degraded-state surface ("trigger unavailable") instead of silent failure.
3. **Raw Input stays the investigated fallback** (documented, no timeout removal, but cannot swallow keys and its delivery during a foreign `DoDragDrop` is undocumented). Swallowing looked unnecessary for Explorer (selection unchanged with and without, 5/5 each; one app, one check), which makes Raw Input viable. E2 is scheduled, not conditional on field data (V1 has no telemetry).
4. **EDR/SmartScreen**: sign the binaries and install per-user into a stable folder; public EDR rules flag unsigned, recently built executables calling `SetWindowsHookEx(WH_KEYBOARD_LL)`. This matters more than hook vs Raw Input.
5. **UIPI**: the trigger does not work while an elevated window is in the foreground; document it, do not work around it (no UIAccess).
