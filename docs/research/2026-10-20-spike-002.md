# Spike 002 — overlay framework (002A), input robustness (002B), memory growth

- **Date:** 2026-10-20. **Code:** `spikes/interaction/` (throwaway). **Raw logs:** `spikes/interaction/results/` (git-ignored; reproducible with `scripts/Run-Scenario.ps1`).
- **Scope of every claim:** one machine (Windows 11 Pro 26200, 12 logical cores), one 1920×1080 monitor at 125 %, injected input, non-elevated, Release builds unless noted, the hardened harness (Spike 001 §R-K). No multi-monitor, no mixed DPI, no Windows 10, no human feel pass.
- **Budgets used:** `docs/performance/budgets.md` (owner, 2026-10-20).

## 002A — WPF dead zone and framework comparison

### Dead-zone hit-testing (WPF host, `--deadzone-alpha`)
| Dead zone | Run | DragEnter without extra movement | Release *inside* the dead zone | Fall-through |
|---|---|---|---|---|
| Unpainted (Spike 001 behaviour) | self, 10 | no: median 349 ms (arrives with the first move) | — | — |
| Painted, alpha 0 | self, 10 + 5 | no: median 348 ms | 0/5 reached the overlay; the source reported a drop onto the window **underneath** | **yes** |
| Painted, alpha 0 | Explorer, 5 | — | harness guard refused 5/5 because `WindowFromPoint` at the ring centre returned **Explorer** | **yes** (would have dropped into Explorer) |
| Painted, alpha 1 (1/255, invisible) | self, 10 + 5 | **yes: median 17.6 ms** | 5/5 received by the overlay (sector −1 = dead zone) | **no** |
| Painted, alpha 1 | Explorer, 10 (3 files) + 5 | yes: median 18.4 ms, p95 29.1 ms | 5/5 received (sector −1); 10/10 sector drops with 3 correct Unicode paths | **no** |
| Win32 opaque circular region (reference) | self, 5 | yes: median 16.8 ms | 5/5 received (sector −1) | no |

Result: a per-pixel-alpha WPF window is click-through for OLE wherever alpha is 0, whether the pixel is unpainted or painted with a fully transparent brush. **Alpha 1 is sufficient** and visually invisible. Rule for the product: every pixel inside the ring has alpha ≥ 1; pixels outside the ring stay alpha 0 (release outside the ring falls through to Explorer, which is the intended "not our drop" behaviour, Spike 001 §R-K).

Corners/edges with alpha 1 (8 points): 8/8 drops; window clamped like the Win32 host; DragEnter at corners only after the cursor moves into the ring (known ADR-0004 item). Focus stolen: **0 of 2458 shows** across all Spike 002 runs.

## 002B — input robustness

### E1: low-level hooks under GC pressure (pressure on a separate thread; hook thread unchanged)
Measured from the harness's injection timestamp to the hook callback's first instruction (same QPC clock in both processes), so a callback blocked by the runtime before managed entry **is** visible (Spike 001 evaluator finding).

| Run (200 cycles each) | GC activity | inject → hook entry p50 / p95 / p99 / max | lost activations at the hook | hook removed? | overlays not shown |
|---|---|---|---|---|---|
| WPF, no pressure (300 cycles) | ~0 | 0.2 / 0.6 / 0.7 / 1.2 ms | 0 | no | 1/300 (no DragEnter, cause not determined) |
| WPF, churn (≈150 MB/s, 128 MB live ring) | 3234 gen0, 3213 gen1, 204 gen2; 11.9 s total pause | 0.3 / 0.7 / 1.5 / 6.6 ms | 0 | no | 9/200 (UI thread stall, max 4.2 s hook→UI) |
| WPF, extreme (+3 M-object graph, forced blocking compacting gen2 every 2 s, max 663 ms) | 158 forced full GCs; 82.6 s total pause | 0.3 / 377 / 467 / 489 ms | 0 | no | 36/200 (UI thread) |
| Win32, extreme + Raw Input | 156 forced full GCs, max 642 ms | 0.4 / 350 / 391 / 401 ms | 0 | no | 0/200 (hook→UI max 468 ms) |

Findings:
1. The hook thread waiting in `GetMessageW` is not what fails: under realistic churn the hook entry stays ≤ 6.6 ms. Only forced blocking full GCs (hundreds of ms) delay the callback, by about the pause length.
2. Windows did **not** remove the hook in 314 runtime suspensions of up to ≈ 550 ms (keyboard and mouse call counts equal the injected event counts, and equal Raw Input's counts). Removal at > 1000 ms (the cap) was not tested: provoking it would need a deliberately slow callback, which this experiment excluded by design.
3. The fragile part is the **UI thread**, not the hook. The WPF stalls first attributed to GC here were later shown to be ≈ 5 s UI-thread blocks inside UI Automation handling (§002C); the Win32 message loop degraded far less (hook→UI max 468 ms).
4. Hook-entry delay under forced blocking GC reached 489 ms and no removal was observed, but removal beyond the timeout was not tested. The risk is **reduced, not eliminated**, by keeping the resident process allocation-light (engines, decoding, thumbnails in the worker).

### E2: Raw Input (Win32 host, `RIDEV_INPUTSINK` on the message-only window)
| Run | Space key-downs seen by Raw Input during the drag | Notes |
|---|---|---|
| Explorer drag, 10 cycles | 10/10 (`RIM_INPUTSINK`, Explorer foreground in `DoDragDrop`) | registration on a message-only window succeeded |
| Self drag, 20 cycles | 20/20 | — |
| Win32 extreme GC, 200 cycles | 200/200; keyboard 400 = hook 400 | — |

Findings: Raw Input keeps arriving during a foreign OLE drag and sees injected input (`hDevice` = 0, so injected and real input are distinguishable). It cannot swallow keys, it needs a window and a pumping thread, and mouse registration makes the process receive every mouse move system-wide. **No latency figure is claimed:** the measured arrival times included queueing behind overlay work on the same thread (evaluator M2), so they are withdrawn. All input was injected; UIPI was not tested.

### Classification
| Mechanism | Decision | Why |
|---|---|---|
| Low-level keyboard + mouse hooks on a dedicated thread | **ADOPT** (primary) | Only mechanism verified end to end; 0 lost activations in every run; survives runtime suspension; can suppress if ever needed |
| Raw Input | **INVESTIGATED FALLBACK, not in V1** | Works during Explorer drags; Windows gives no hook-removal notification to pair it with; no suppression; latency not established (M2) |
| Hybrid (hook primary + Raw Input keyboard as health oracle) | **DEFERRED** | A plausible event-driven hook-loss detector; not built in V1 (owner decision 2026-10-21). Hook health/recovery stays a future reliability requirement. |

**Operational failure mode (future design, not built in V1):** if Windows removes a hook (callback blocked > the timeout, which in practice means a resident-process stall of ≈ 1 s), the next key press is seen by Raw Input but not by the hook; the app re-installs both hooks from the hook thread, records the event in the local log, and shows a degraded state if re-installation fails. That trigger press is lost; the following one works. The detection path was **not** exercised against a real removal in this spike; the product must test it with a debug-only fault injection (a deliberately stalled callback).

## Memory growth (Part E)
Win32 host, Release, 1500 cycles, **full GC before every 10 s sample**:

| Sample | Cycles (approx.) | Private MB | Working set MB | Managed heap MB | GDI / USER / handles |
|---|---|---|---|---|---|
| 10 s | 4 | 11.4 | 41.0 | 0.55 | 4 / 14 / 310 |
| 210 s | 150 | 10.4 | 41.6 | 0.59 | 4 / 14 / 312 |
| 410 s | 300 | 9.2 | 41.0 | 0.59 | 4 / 15 / 314 |
| 1210 s | 890 | 9.3 | 41.2 | 0.59 | 4 / 15 / 315 |
| 2011 s | 1475 | 9.1 | 41.0 | 0.59 | 4 / 14 / 311 |
| end + 30 s idle | 1500 | 9.7 | 41.6 | 0.59 | 4 / 14 / 313 |

Conclusion: **no per-cycle growth.** With collection forced before each sample, private bytes plateau at ≈ 9.2 MB from cycle ≈ 300 to 1500, the live managed heap is flat at 0.59 MB, and GDI/USER/handles are flat. The ≈ 2 MB "native" growth seen in Spike 001 was managed-heap behaviour (garbage not yet collected plus memory the GC keeps committed between collections), not a leak. The budget's "0 growth over 1000 cycles" is met when measured after a collection.

## Evaluator review (2026-10-20)
Verdict: ADR-0001 not acceptable yet; ADR-0003 acceptable with amendments; first slice CONDITIONAL GO for the framework-independent parts only (session, resolver, PNG→JPG command, worker with WIC, output writer). Overlay and tray stay NO-GO until ADR-0001 is resolved.
- **B1 (blocker):** all WPF overlay losses trace to 14 UI-thread blocks of 5.00–5.02 s between overlay.show and the first render. That is not GC (pauses average 3.7 ms, max 663 ms). The GC-stall explanation and ADR-0001 rule 3 are withdrawn. Root cause still open.
- **M1:** in WPF, a drop is only received after a frame has been presented. During B1 the source saw effect NONE (12/200, 49/200). A fast-release race test (0–50 ms, 1000 cycles, Explorer) is required for both hosts.
- **M2:** the Raw Input latency measured queueing behind overlay work and is withdrawn. All input was injected; UIPI was not tested.
- **M3:** "no removal" is limited. Time inside the callback reached 468–521 ms; entry plus callback time was not logged.
- **M4:** the memory plateau was measured only on Win32 with forced GC. WPF grew 86→95 MB private over 300 cycles.
- **M5:** the WPF host allocates in the hook callback, so it does not represent the proposed design. WPF startup of 420–588 ms fails the 500 ms budget.
- **M6:** RegisterHotKey armed only during a drag is a simpler, unevaluated option.
- **Minor:** a dead-zone drop must return NONE; the harness must count drops by effect; stale decisions must be discarded; the build configuration must be logged; the corner DragEnter p95 is over budget.

## 002C — WPF five-second stall, watchdog control, fast release (2026-10-20/21)
A time-boxed follow-up to evaluator blocker B1. All of the instrumentation is diagnostic only, not product behaviour: `StallProbe`, `--probe-stalls`, `--watchdog-ms`, `--no-uia`, `--fast-release`.

**Method.** A background thread sends two heartbeats to the WPF UI thread every 50 ms:
- a dispatcher operation at `Send` priority;
- a plain posted message to a message-only window.

A dispatcher operation that runs at least 1 s late is logged as a stall. While it is overdue, the UI thread is sampled at about 1.0, 2.5 and 4.0 s. Each sample suspends the thread for less than 1 ms, copies its registers and the top of its stack, and resumes it. Symbols are resolved afterwards, from module exports only. Every `WM_GETOBJECT` that arrives at the overlay window is logged.

**Reproduction (WPF, self harness, `extreme` GC pressure):**

| Run | Cycles | Stalls ≥ 1 s | Stall length | Drops lost after show (effect NONE) | `AwaitDrop` watchdog |
|---|---|---|---|---|---|
| no load (2 runs) | 50 + 30 | 0 | — | 0 | 5000 ms |
| extreme | 200 | 9 | 4958–5021 ms | 9 | 5000 ms |
| extreme + `WM_GETOBJECT` log | 120 | 9 | 5005–5017 ms | 9 | 5000 ms |
| extreme, watchdog 2000 | 150 | 7 | 5008–5026 ms | 7 | **2000 ms** |
| extreme, watchdog 8000 | 150 | 10 | 4743–5028 ms | 11 | **8000 ms** |
| extreme, overlay answers `WM_GETOBJECT` with 0 (`--no-uia`) | 200 | **0** | — | **0** (200/200 drops) | 5000 ms |

Findings:
1. **This is a real UI-thread stall, not the interaction watchdog.**
   - The stall stayed at about 5.0 s whether the watchdog was set to 2, 5 or 8 s.
   - In every one of the 105 stack samples, the probe's message window had handled nothing for at least (sample age − 0.7 s).
   - The dispatcher heartbeat was blocked for the whole interval. Dispatcher work, rendering and ordinary posted messages all stopped.
2. **Where the thread was.** The sampled call chain was:
   - `GetMessageW` receives a `WM_GETOBJECT`. Another process's UI Automation client sends it about 0.3–0.5 ms after `overlay.show`.
   - `UIAutomationCore` calls WPF's managed UIA provider.
   - The provider ends in a CLR wait on the STA (`CoWaitForMultipleHandles`, a COM modal loop).

   In the runs that logged it, every stall (26/26) began with a `WM_GETOBJECT` right after the show. The UIA burst (`OBJID_CLIENT`, `OBJID_WINDOW`, the UIA root) completed immediately after each stall ended.
3. **It is correlated with heavy managed pressure.** There were 0 stalls in 80 unloaded cycles, even though `WM_GETOBJECT` arrived on every show there too (310 queries).
4. **Causal A/B.** With UIA exposure disabled for the overlay, the same pressure produced 0 stalls and 200/200 drops.
5. **Not determined, and not pursued further** (owner decision 2026-10-21): what the CLR wait was waiting for, and why it lasted about 5 s. Answering that needs runtime symbols.
6. **Rejected path.** Disabling UI Automation is not an acceptable product strategy, because it removes accessibility. WPF is therefore not chosen for this overlay (ADR-0001). This finding is about this global drag/drop overlay in a resident process. It is not a claim that WPF is generally unreliable.

**Fast release (self harness, both hosts, no load).** The trigger key goes down, and the button is released 0, 10, 25 or 50 ms later (busy-wait timing). The release happens either on the spot or after a jump to a sector.

| Release after trigger | Win32: overlay drop / released before the overlay existed | WPF: overlay drop / released before the overlay existed |
|---|---|---|
| 0 ms (150 cycles) | 76 / 74 | 100 / 50 |
| 10 ms (150) | 130 / 20 | 129 / 21 (1 before first paint) |
| 25 ms (150) | 147 / 3 | 144 / 2 (4 cycles invalid: the drag ended before the trigger) |
| 50 ms (150) | 150 / 0 | 150 / 0 |
| **lost after the overlay was shown and painted** | **0** | **0** |

A release made before our window exists belongs to the window underneath, which is Windows' normal behaviour. Once the overlay was available, neither host lost a drop.

**Explorer fast release was not obtained**, because of two harness defects:
- **(a)** The release guard was evaluated before the key-down, when the overlay could not exist yet. As a result, every Win32 Explorer release was refused and converted to Escape.
- **(b)** After a refused release, the next cycle's button-down on the same file completed a double-click. This **opened the sample `plain.txt` in Notepad** once. No file content changed (the sample-folder check passed after every run), and the Notepad window was closed. The WPF Explorer runs then refused to start, because that window covered the drag point.

Both defects are fixed in the harness. The guard is now evaluated at the release instant, and every cancelled drag is followed by a pause longer than the double-click time. The fix has not been re-run; this test moves to the product acceptance tests.

**WPF memory with the agreed method is incomplete.** The 1500-cycle run (full GC before each sample) stopped after 236 cycles, when the harness process exited with an unhandled .NET exception (`0xE0434352`, not investigated). Over those 236 cycles:
- private bytes went from 86.7 to 85.7 MB;
- working set went from 133 to 136.5 MB.

That is inside the 120 MB ceiling and not growing, but the run is too short to call a plateau.
