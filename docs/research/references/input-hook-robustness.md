## 1. Facts with citations

### 1.1 Low-level hooks (F1-F10)

- **F1 — Called on the installing thread, which must pump messages.** "This hook is called in the context of the thread that installed it. The call is made by sending a message to the thread that installed the hook. Therefore, the thread that installed the hook must have a message loop." ([LowLevelKeyboardProc], same text in [LowLevelMouseProc]) Consequence (Raymond Chen 2015): a watchdog that re-installs the hook from a thread-pool thread gets a hook that "succeeds" but never fires, and "if the pool trims the thread, the hook disappears with it". Re-installation must happen on a thread we own that pumps.
- **F2 — Timeout and silent removal.** "The hook procedure should process a message in less time than the data entry specified in the LowLevelHooksTimeout value in the following registry key: HKEY_CURRENT_USER\Control Panel\Desktop. The value is in milliseconds. If the hook procedure times out, the system passes the message to the next hook. However, on Windows 7 and later, the hook is silently removed without being called. There is no way for the application to know whether the hook is removed." ([LowLevelKeyboardProc]/[LowLevelMouseProc])
- **F3 — Cap since 1709.** "Windows 10 version 1709 and later: The maximum timeout value the system allows is 1000 milliseconds (1 second). The system will default to using a 1000 millisecond timeout if the LowLevelHooksTimeout value is set to a value larger than 1000." (same pages). The default when the value is absent is **not documented** on Learn (see §7).
- **F4 — Microsoft's own guidance.** "If the application must use low level hooks, it should run the hooks on a dedicated thread that passes the work off to a worker thread and then immediately returns. In most cases where the application needs to use low level hooks, it should monitor raw input instead. This is because raw input can asynchronously monitor mouse and keyboard messages that are targeted for other threads more effectively than low level hooks can." (same pages)
- **F5 — Injected input is visible and flagged.** "The keyboard input can come from the local keyboard driver or from calls to the keybd_event function. If the input comes from a call to keybd_event, the input was 'injected'." ([LowLevelKeyboardProc]). `KBDLLHOOKSTRUCT.flags`: "Testing LLKHF_INJECTED (bit 4) will tell you whether the event was injected. If it was, then testing LLKHF_LOWER_IL_INJECTED (bit 1) will tell you whether or not the event was injected from a process running at lower integrity level." Same for `MSLLHOOKSTRUCT` (`LLMHF_INJECTED`, `LLMHF_LOWER_IL_INJECTED`). `MSLLHOOKSTRUCT.mouseData` high word carries `XBUTTON1`/`XBUTTON2` for `WM_XBUTTONDOWN/UP`, and `WM_XBUTTONDOWN`/`WM_XBUTTONUP` are in the documented `wParam` list of LowLevelMouseProc.
- **F6 — Return values.** nCode < 0 must be passed to `CallNextHookEx`; "If the hook procedure processed the message, it may return a nonzero value to prevent the system from passing the message to the rest of the hook chain or the target window procedure." `CallNextHookEx`'s `hhk` "parameter is ignored." Not chaining means "other applications that have installed hooks will not receive hook notifications and may behave incorrectly".
- **F7 — Scope and chain.** WH_KEYBOARD_LL / WH_MOUSE_LL are "Global only"; "thread hooks are called first, then global hooks"; "The global hooks are a shared resource, and installing one affects all applications in the same desktop as the calling thread." For LL hooks there is no DLL injection: "the WH_KEYBOARD_LL hook is not injected into another process. Instead, the context switches back to the process that installed the hook and it is called in its original context." ([SetWindowsHookExW], [LowLevelKeyboardProc])
- **F8 — .NET delegate lifetime.** "In .NET apps, you must ensure the callback is not moved around by the garbage collector (otherwise your app will crash with an ExecutionEngineException)." ([SetWindowsHookExW]). The spike keeps `_kbProc`/`_mouseProc` in fields (`LowLevelHooks.cs` L16-17), which is sufficient; delegates are not moved, they must only stay reachable.
- **F9 — Unhook semantics.** "The hook procedure can be in the state of being called by another thread even after UnhookWindowsHookEx returns. If the hook procedure is not being called concurrently, the hook procedure is removed immediately before UnhookWindowsHookEx returns." ([UnhookWindowsHookEx]) Failure returns zero with `GetLastError`.
- **F10 — Hooks run before the input is queued; `GetMessage` delivers sent messages while waiting.** "The system calls this function every time a new keyboard input event is about to be posted into a thread input queue." ([LowLevelKeyboardProc]). "During this call, the system delivers pending, nonqueued messages" ([GetMessageW]); the hook call is such a sent-message delivery (F1), which is why a thread blocked in `GetMessageW` runs hook callbacks without returning from `GetMessageW`.

### 1.2 .NET GC and native waits (F11-F16)

- **F11 — Threads in native code are not suspended.** "Threads that run native code are not suspended on either server or workstation garbage collection." ([Workstation vs server GC]). BotR: "Generally, native code does not touch managed objects, and thus runs in preemptive mode"; "A GC may only proceed when all managed threads are in 'preemptive' mode (not holding the lock)"; hijacking "attempts to force any managed thread that is currently running in cooperative mode, to leave cooperative mode at a 'safe point'." ([BotR threading])
- **F12 — Re-entering managed code during a GC blocks.** "If a GC is in progress (the GC holds the lock) then block until the GC is complete." "Any threads that attempt to enter cooperative mode will block until the GC is complete." ([BotR threading]). A reverse-P/Invoke (user32 calling our `HookProc` delegate thunk) is exactly such an entry.
- **F13 — What suspends whom.** "Before a garbage collection starts, all managed threads are suspended except for the thread that triggered the garbage collection." ([GC fundamentals]). Background GC: "A collection on ephemeral generations during background garbage collection is known as foreground garbage collection. When foreground garbage collections occur, all managed threads are suspended." "Background garbage collection is enabled by default." ([Background GC]). "generations 0 and 1 are always non-concurrent because they finish fast." (same page, concurrent-GC section)
- **F14 — Latency modes.** Workstation default is `Interactive` ("For most applications that have a UI. This is the default mode"). `SustainedLowLatency` "suppresses foreground generation 2 collections and performs only generation 0, 1, and background generation 2 collections. It can be used for longer periods of time... This setting cannot be used if background garbage collection is disabled." `LowLatency` "can be used only for short periods of time" and "is available only for workstation garbage collection." ([Latency modes])
- **F15 — Pause measurement exists.** `GC.GetTotalPauseDuration()` (.NET 7+): "Gets the total amount of time paused in GC since the beginning of the process." Runtime events `GCSuspendEEBegin_V1` (ID 9, "Start of suspension of the execution engine for garbage collection"), `GCSuspendEEEnd_V1` (8), `GCRestartEEBegin_V1` (7), `GCRestartEEEnd_V1` (3, "Resumption from common language runtime suspension has ended"), `GCStart_V1` carries `Type` (0 blocking, 1 background, 2 blocking-during-background) and `Reason`. ([GC runtime events])
- **F16 — Realistic pause lengths are not documented.** No Microsoft page gives numbers for a small-heap desktop app. "The intrusiveness (frequency and duration) of garbage collections is the result of the volume of allocations and the amount of survived memory on the managed heap." ([GC fundamentals]) Measurement is required (§6).

### 1.3 Raw Input (F17-F22)

- **F17 — Background delivery.** `RIDEV_INPUTSINK` (0x100): "If set, this enables the caller to receive the input even when the caller is not in the foreground. Note that hwndTarget must be specified." `RIDEV_EXINPUTSINK` (0x1000): "enables the caller to receive input in the background only if the foreground application does not process it." ([RAWINPUTDEVICE]). "An application can receive data when it is in the foreground and when it is in the background (if registered with RIDEV_INPUTSINK)." ([Raw Input overview]). `WM_INPUT` wParam: `RIM_INPUT` (0) "Input occurred while the application was in the foreground. The application must call DefWindowProc so the system can perform cleanup." `RIM_INPUTSINK` (1) "Input occurred while the application was not in the foreground." ([WM_INPUT])
- **F18 — No swallowing.** `RIDEV_NOLEGACY` only affects the registering application: "If RIDEV_NOLEGACY is set for a mouse or a keyboard, the system does not generate any legacy message for that device for the application." ([RAWINPUTDEVICE]) Raw Input has no return-value path to block an event for other windows. Legacy delivery to the foreground window is untouched.
- **F19 — What it sees.** Keyboard: `RAWKEYBOARD.MakeCode`, `Flags` (`RI_KEY_MAKE`/`RI_KEY_BREAK`/E0/E1), `VKey` ("The corresponding legacy virtual-key code"), `Message` (e.g. `WM_KEYDOWN`), `ExtraInformation`. Mouse: `RAWMOUSE.usButtonFlags` includes `RI_MOUSE_BUTTON_4_DOWN` (0x0040, "XBUTTON1 changed to down"), `RI_MOUSE_BUTTON_5_DOWN` (0x0100, "XBUTTON2 changed to down"), left/middle/right up/down, wheel; motion is relative (`MOUSE_MOVE_RELATIVE`) with no pointer ballistics ("WM_INPUT has no ballistics applied to its data" — [High-definition mouse movement]). There is no documented "injected" flag in `RAWKEYBOARD`/`RAWMOUSE`; `ExtraInformation` is "device-specific additional information".
- **F20 — No timeout, no removal.** Raw Input is a queued message (`QS_RAWINPUT`); the Raw Input pages contain no timeout or deregistration-on-slowness clause. A slow consumer only delays its own queue.
- **F21 — One window per device class per process; not for libraries.** "Only one window per raw input device class may be registered to receive raw input within a process (the window passed in the last call to RegisterRawInputDevices). Because of this, RegisterRawInputDevices should not be used from a library." ([RegisterRawInputDevices])
- **F22 — Microsoft explicitly prefers it over LL hooks** for monitoring (F4).

### 1.4 RegisterHotKey (F23)

- **F23.** "When a key is pressed, the system looks for a match against all hot keys. Upon finding a match, the system posts the WM_HOTKEY message to the message queue of the window with which the hot key is associated." Fails "if the keystrokes specified for the hot key have already been registered for another hot key." `MOD_NOREPEAT` exists; F12 is reserved; modifiers are optional per the signature ("can be a combination of"). ([RegisterHotKey]) Nothing is documented about behaviour while another process runs a `DoDragDrop` modal loop, and a hot key is consumed system-wide for as long as it is registered — Space as a bare hot key would be eaten everywhere unless registered only during a drag, which needs another detector to know a drag started.

### 1.5 UIPI / elevation (F24-F26)

- **F24.** "User Interface Privilege Isolation (UIPI) implements restrictions in the windows subsystem that prevents lower-privilege applications from sending window messages or installing hooks in higher-privilege processes." A lower-privilege process cannot: "Use thread hooks to attach to a process running with higher rights. Use journal hooks to monitor a process running with higher rights. Perform dynamic link library (DLL) injection to a process running with higher rights." ([Windows Integrity Mechanism Design])
- **F25.** A UIAccess process "Has read input for all integrity levels using low-level hooks, raw input, GetKeyState, GetAsyncKeyState, and GetKeyboardInput." (same page). The page does not state the converse in one sentence, but listing it as a UIAccess privilege is the official basis for the widely observed behaviour that a medium-IL LL hook or Raw Input sink does **not** see input directed at a higher-IL window. Our rules forbid UIAccess and elevation, so this is a hard limitation to accept and document.
- **F26.** `SendInput` "is subject to UIPI. Applications are permitted to inject input only into applications that are at an equal or lesser integrity level." "This function fails when it is blocked by UIPI. Note that neither GetLastError nor the return value will indicate the failure was caused by UIPI blocking." ([SendInput]) This matters for any self-probe that injects a marker key (§3, Q1).

### 1.6 AV / EDR (F27-F30)

- **F27 — Elastic Defend (public rules, response = kill).** Rule "Keystrokes Input Capture via SetWindowsHookEx": process start where the binary was created/modified within 900 s **and** `code_signature.trusted == false or code_signature.exists == false`, followed within 1 min by `SetWindowsHookEx` with `hook_type == "WH_KEYBOARD_LL"`, `call_stack_final_user_module.name == "Unknown"`, and `hook_module` not under `Program Files`, `Program Files (x86)` or `Windows`. Response action: `kill_process`. (rule TOML, v1.0.3)
- **F28 — Elastic rule aimed at .NET.** "Keystrokes Input Capture from a Managed Application": recent (500 s) unsigned/untrusted process, then `GetAsyncKeyState` **or** `SetWindowsHookEx(WH_KEYBOARD_LL)` where the call stack's final user module is "Unbacked" with protection provenance `clr.dll` (i.e. the call originates from JIT-compiled managed code); executables under `Program Files` are excluded; parent `devenv.exe` excluded. Response: kill process. (rule TOML, v1.0.7) A freshly built, unsigned .NET spike that P/Invokes `SetWindowsHookEx` from managed code matches this rule on a machine running Elastic Defend.
- **F29 — Raw Input is also watched.** Rule "Keystroke Input Capture via RegisterRawInputDevices" (query reproduced in the Elastic article): `not process.code_signature.status : "trusted"`, `RegisterRawInputDevices` with keyboard usage and flags containing `INPUTSINK`, call-stack module not under `Program Files`/`System32`/`SysWOW64`/`SystemApps`, executable not under `Program Files`. Elastic lists ten keylogger rules in total, covering `GetAsyncKeyState`, `SetWindowsHookEx`, `RegisterRawInputDevices` and DirectInput; detection is via "Event Tracing for Windows (ETW)".
- **F30 — Microsoft Defender / SmartScreen.** No public Microsoft document describing a Defender heuristic on `SetWindowsHookEx(WH_KEYBOARD_LL)` was found (§7). SmartScreen's documented criteria are reputation-based: it checks "downloaded programs and the digital signature used to sign a file. If a URL, a file, an app, or a certificate has an established reputation, users don't see any warnings. If there's no reputation, the item is marked as a higher risk and presents a warning to the user." It does not inspect runtime API behaviour. ([SmartScreen overview])

## 2. What each studied project does

### PowerToys (C++ with C# modules)
- **Interop hook for C# consumers** — `src/common/interop/KeyboardHook.cpp`: `SetWindowsHookEx(WH_KEYBOARD_LL, HookProc, 0, 0)` on whatever thread calls `Start()` (consumer: `KeyboardManagerEditorUI/Controls/UnifiedMappingControl.xaml.cs`, i.e. the UI thread). Single static hook shared by instances; `DISABLE_LOWLEVEL_HOOKS_WHEN_DEBUGGED` skips the hook under a debugger (a debugger break would otherwise trip the timeout). No health check, no re-install.
- **Runner's centralized hotkey hook** — `src/runner/centralized_kb_hook.cpp`, started from `src/runner/main.cpp:229` on the runner's main (tray/message-loop) thread, `SetWindowsHookExW(WH_KEYBOARD_LL, KeyboardHookProc, NULL, NULL)`. Runs module actions **inside** the hook procedure (`action()` at the match), then injects a dummy `VK 0xFF` key-up via `SendInput` with a `dwExtraInfo` marker so the Start menu does not open, and swallows the key (`return 1`). No watchdog.
- **Keyboard Manager engine** — a separate process (`KeyboardManagerEngine.exe`, `KeyboardManagerEngine/main.cpp`): the main thread pumps messages (`run_message_loop`) and owns the hooks; settings changes post `StartHookMessageID` so that `SetWindowsHookEx` runs on the hook thread (`KeyboardManager.cpp` L66-81, comment: "SetWindowsHookEx must run on the hook thread"). Hooks are installed/removed only on configuration changes; no timeout watchdog.
- **Mouse utilities** — each installs its own `WH_MOUSE_LL` from its worker thread and logs failure (`MouseHighlighter.cpp:854`, `CursorWrap/dllmain.cpp:492`, `InclusiveCrosshairs.cpp:403`). No watchdog.
- **Mouse Without Borders (C#)** — `App/Class/InputHook.cs` installs both LL hooks with managed delegates from a hidden WinForms form on a dedicated "InputCallback" thread (`Form/frmInputCallback.cs:55-80`; the comment cites the MSDN timeout and says the message-loop thread should be high priority, but the priority line is commented out). Hooks are torn down and re-created (`Core/Common.cs:1270-1286`, `Hook.Stop()` then `InstallKeyboardAndMouseHook()`) when sockets are reopened after read errors — a side effect of reconnection, not a hook-health check.
- **Issue tracker evidence** (search strings in §Sources): #38089 "Keyboard Manager shortcuts stop working after a few minutes" (root-caused by a user in 2026 to Quick Accent swallowing a key-up, not to hook loss — a reminder that "hook dead" symptoms have other causes), #37380 "Remapping temporarily stops working under high CPU load" (open, no root cause), #40423 "Keyboard Manager hangs multiple times a day" (input lags for seconds, then remaps stop; needs PowerToys restart), #50678 "randomly stops working", #23231 (comment by `monoblaine` attributing loss to `LowLevelHooksTimeout` and recommending `reg add ... /d 1000`; a later user reports 1000 ms did not help), #50980 "CmdPal: Move the low-level keyboard hook to a separate thread" (open, 2026-10-03: hook on the UI thread, "if that freeze Windows can throw the hook away"). Pattern: a mature, signed, Program-Files-installed product still gets "stops working" reports consistent with silent removal and has **no** detection/re-install mechanism anywhere in the tree.

### AutoHotkey (C++)
- `source/hook.cpp`: both hooks live on a dedicated thread created with an 8 KB stack and **`THREAD_PRIORITY_TIME_CRITICAL`** ("if some other process has high priority, the keyboard and mouse hooks will still take precedence, which avoids the mouse cursor and keystroke lag that would otherwise occur (confirmed through testing)"), L3879-3900. Hook state changes are requested by posting `AHK_CHANGE_HOOK_STATE` to that thread; `HookThreadProc` (L4093+) installs/uninstalls inside its own `GetMessage` loop and reports failure back to the main thread.
- Removal awareness: on uninstall it accepts `ERROR_INVALID_HOOK_HANDLE` as success "in case the OS has already removed the hook" (L4131, L4146). That is the only acknowledgement of OS removal; there is **no periodic re-install and no watchdog**. The hook itself never blocks: hotstring replacement is posted to the main thread because a slow callback "would cause the OS to think the hook is unresponsive, which in turn would cause it to timeout and route the key through anyway (testing confirms this)" (L2549-2553).
- Issue search ("hook stops working", "hook") returned nothing relevant on the GitHub tracker (AHK triage lives on its forum, not checked).

### libuiohook / SharpHook (C + .NET wrapper)
- `src/windows/input_hook.c`: `hook_run()` installs both LL hooks on the calling thread (SharpHook runs it on a thread it creates) and pumps `GetMessage`. It additionally registers a `SetWinEventHook(EVENT_OBJECT_NAMECHANGE, ...)` and on **every** such event unhooks and re-installs both hooks ("Restarting Windows input hook on window event", L596-632) with a `FIXME` about missed modifier state. No rationale is recorded in the tree or the commit history reachable at depth 1 (§7); it is a blind periodic re-install keyed to an unrelated, frequent UI event.
- SharpHook issue #84 "Hook events stop working after using SendInput from the win32 API" (closed, no reproduction); no issue mentions the timeout or GC. globalmousekeyhook (`HookHelper.cs`) installs from the calling thread with `Process.GetCurrentProcess().MainModule.BaseAddress` as hMod and has no health logic; its issues are about usage, not loss.

### Action-Wheel (C#/WinUI, the closest analogue)
- `Services/MouseHook.cs` / `Services/KeyboardHook.cs`: LL hooks installed on the UI thread (`DispatcherQueue`), managed delegates kept in fields, `LastCallbackTick` updated on every callback, blittable struct dereference instead of `Marshal.PtrToStructure` with a comment explicitly about avoiding Gen0 garbage "inside the one callback Windows times against LowLevelHooksTimeout".
- `Services/LauncherService.cs` L151-191: a 5 s dispatcher timer compares cursor position with `LastCallbackTick`; "Cursor movement is a safe probe: a live mouse hook must observe it. If Windows removed the hook after a timeout, the cursor moves while LastCallbackTick stays unchanged." On mismatch it unhooks and re-installs **both** hooks from the UI thread. Weaknesses for us: the keyboard hook's health is inferred from the mouse hook's (they are removed independently), the probe needs the user to move the mouse, and the hooks share the UI thread's stalls.

## 3. Answers to the six questions

### Q1. When does Windows remove a low-level hook, and is removal detectable?
- **Removal conditions (documented):** the hook procedure does not return within `LowLevelHooksTimeout` (F2, capped at 1000 ms since 1709, F3). Also implicitly: the installing thread exits (hook has thread affinity, F1/Raymond Chen), and the process exits. Nothing else is documented; session lock/unlock, sleep/resume and desktop switches are *reported* loss moments in PowerToys issues but not documented causes.
- **Detectability:** "There is no way for the application to know whether the hook is removed." (F2). `SetWindowsHookEx` succeeding again is not a signal (it always succeeds on a pumping thread). Practical signals, all heuristic:
  1. *Lack of callbacks while input provably happened* — Action-Wheel's cursor-vs-callback probe (§2); keyboard analogue would be `GetAsyncKeyState`/`GetKeyboardState` deltas without callbacks, which needs polling.
  2. *Self-probe:* inject a harmless marker key (`SendInput`, `VK 0xFF` key-up with a `dwExtraInfo` marker, as PowerToys' runner already does for another reason) and require the hook to see it (F5 guarantees LL hooks see injected input with `LLKHF_INJECTED`). Deterministic and needs no user action; caveats: `SendInput` is silently dropped when the foreground window is higher-IL (F26), so a missed probe must be confirmed (e.g., twice, or only when the foreground process is medium IL) before declaring the hook dead; and each injection is one more "synthetic input" ETW event for an EDR to correlate.
  3. *`UnhookWindowsHookEx` failing with `ERROR_INVALID_HOOK_HANDLE` (1404)* — AutoHotkey treats this as "the OS already removed the hook". Only usable at re-install time (it is destructive), and whether OS removal invalidates the handle is unverified (§7).
- **Mouse and keyboard hooks are separate chains with separate timeouts**; a mouse-hook probe says nothing about the keyboard hook.

### Q2. Does the GC block a hook callback that is waiting in native `GetMessageW`, or only one executing managed code? Realistic worst case?
- A thread blocked in `GetMessageW` is in **preemptive** mode and is neither suspended nor waited for (F11). The GC proceeds without it.
- When user32 delivers the hook call (a sent message dispatched *inside* `GetMessageW`, F10) the thread enters our managed delegate through a reverse-P/Invoke thunk, i.e. it tries to enter **cooperative** mode. If a GC is in progress at that instant, **the entry blocks until the GC completes** (F12). If the callback is already executing managed code when a GC starts, it is suspended at a safe point (F11/F13). Either way the callback's wall time as seen by Windows = our work + whatever remains of the GC's stop-the-world window.
- So the evaluator's concern is real but narrower than "the hook thread is suspended during every GC": the hazard is only **GC suspension time overlapping a callback**, and the exposure is proportional to callback frequency (the mouse hook fires at the mouse report rate, up to 1000 Hz; the keyboard hook rarely) times blocking-pause length. Dedicated-thread, zero-allocation callbacks (as in the spike) do not remove the exposure; they only remove the "our own work" term.
- **Realistic worst case is undocumented** (F16). What the documentation does say: gen0/gen1 collections are always blocking but "finish fast" (F13); gen2 is background by default with only brief suspensions, but *foreground* (blocking) gen2 still happens (induced, low memory, LOH pressure, or `Batch` latency mode). A multi-hundred-millisecond blocking gen2 on a small (< 100 MB) heap would be unusual but is exactly the case nobody has numbers for; the spike measured ≈2–3 MB growth per 95 cycles and never logged GC pauses. **This is the single measurement that decides the design**; see §6 E1. Mitigations that are documented: `GCSettings.LatencyMode = SustainedLowLatency` suppresses foreground gen2 for long periods on workstation GC with background GC enabled (F14); keep the overlay/engine allocation churn out of the process that owns the hook (§5).
- Second-order: GC is not the only stop-the-world. Debugger attach, `GCSuspendEEBegin` reasons 0x2-0x7 (shutdown, code pitching, debugger) also suspend; any page-in of our code after sleep can stall the first callback. A watchdog must be designed for "any stall", not GC specifically.

### Q3. Is periodic `UnhookWindowsHookEx` + `SetWindowsHookEx` safe? Costs and side effects?
- **Safe if done on the owning, message-pumping thread** (F1; Raymond Chen's failure case was precisely a re-install from a pool thread). libuiohook, AutoHotkey (on state change), Action-Wheel and Mouse Without Borders all do it this way; none reports breakage from the re-install itself.
- **Costs/side effects:**
  - A gap between unhook and re-hook in which input is not observed (microseconds on an idle machine; unmeasured under load). A modifier or button transition inside the gap is lost — libuiohook's `FIXME` ("compare the modifier mask before and after the restart") is about exactly this. For us, a re-install must never happen while a drag session is active.
  - A callback may still be executing when unhook returns (F9); the delegate must stay alive across the swap and the new `HHOOK` must not be used by the old callback (`CallNextHookEx` ignores `hhk`, F6, so the spike's `_hKb` use is harmless).
  - Position in the global chain changes (new hooks are inserted ahead of older ones; this ordering is folklore, not documented — §7). Re-installing on a timer means we periodically jump ahead of other tools (PowerToys, AHK) that were installed after us, changing who sees/swallows the key first. Blind periodic re-install is therefore an anti-social default; re-install **on evidence** (Q1 signals) or on known loss moments (session unlock, resume) is defensible.
  - Each `SetWindowsHookEx` call is an ETW/EDR API event (F27-F29). The Elastic rules key on the first minute after a *recent, unsigned* process start, so later re-installs do not re-trigger those particular rules, but other vendors' heuristics are unknown. Fewer installs is better.
  - Raymond Chen's verdict stands: the real fix is to never exceed the timeout; a watchdog is a safety net, not the mechanism.

### Q4. Is Raw Input (`RIDEV_INPUTSINK`) a viable trigger detector during an OLE drag? What does it lose?
- **For:** delivered while we are in the background (F17); sees keyboard keys with `VKey`/`Message` and mouse X buttons (`RI_MOUSE_BUTTON_4/5_DOWN`, F19); no timeout and no silent removal (F20); Microsoft recommends it over LL hooks for monitoring (F4); it is queued, so a GC stall delays it instead of killing it. Elevation limits are the same as for hooks (F25). It also gives us the mouse motion/button stream to infer "a drag may be starting" (left down + movement) without a mouse hook.
- **Unknowns (no official text; need the experiment, §6 E2):** (a) whether `WM_INPUT` keeps arriving while *another process* is inside `DoDragDrop` with mouse capture — capture affects legacy mouse messages, and Raw Input is documented to bypass legacy routing, but it is not stated for this case; (b) whether `SendInput`-injected events show up in Raw Input and how (`hDevice == NULL`?) — needed for the harness and for any self-probe; (c) whether `RIDEV_INPUTSINK` delivers keyboard input while the foreground is a UWP/`ApplicationFrameHost` window.
- **Loses:** the ability to swallow the trigger key (F18). With Raw Input alone, Space/X1 also reaches the drag source's thread. The spike did not establish what Explorer does with a Space key-down during its drag loop (the drag protocol ignores non-modifier keys, Spike fact 1, but the Explorer window still receives `WM_KEYDOWN`); the evaluator's finding 11 already rules out blanket swallowing, so the product only needs to swallow when the overlay consumed the key — which a Raw-Input-only design cannot do at all. Also loses `LLKHF_INJECTED` (no injected flag in `RAWKEYBOARD`).
- **Verdict:** viable as the *always-on detector*; not viable as the *only* mechanism if swallowing the consumed trigger is required. See option F in Q5 and §5.

### Q5. Where should the hook live?

| Option | Latency to overlay | GC exposure of the callback | Crash isolation | AV/EDR footprint | Complexity |
|---|---|---|---|---|---|
| A. LL hook, managed callback, main process (today) | lowest (in-proc; spike: hook→shown 7–20 ms) | full: every blocking pause of the main heap (UI, engines' marshalling, job bookkeeping) overlaps callbacks | none (hook code is tiny, but a main-process crash kills the trigger too) | matches the ".NET managed application" rule when unsigned and outside Program Files (F28) | lowest |
| B. LL hook in a native DLL, main process | same | **none** for the callback itself (native code never enters cooperative mode, F11); the hand-off to managed code (PostThreadMessage/event) is asynchronous | none | `hook_module` becomes a backed native DLL; still the generic unsigned/outside-Program-Files rule (F27) | adds a C/C++ (or Rust) toolchain to a .NET-only build; forbidden-by-default new dependency path (`dependencies.md`) |
| C. LL hook in a helper process (managed, tiny heap) | + one IPC hop (unmeasured; named-pipe round trips on the same box are typically well under the 50 ms budget, **to be measured**) | only the helper's own GC; a helper that allocates nothing per event and runs `SustainedLowLatency` has a pause profile that is small and measurable in isolation | yes: main-process crash/hang/GC storm cannot kill the hook; helper crash is recoverable by respawn | two processes installing hooks/raw input; both need signing; same rules | moderate: spawn, supervise, IPC framing, versioning; mirrors the worker model ADR-0005 already needs |
| D. Raw Input (`RIDEV_INPUTSINK`), main process | lowest | GC delays the `WM_INPUT` dequeue (adds latency) but **cannot remove** the registration | none needed for liveness | `RegisterRawInputDevices` + `INPUTSINK` rule (F29) | low |
| E. `RegisterHotKey` | lowest | none | none | lowest (no hook, no raw input) | low, but a bare key (Space) would be eaten system-wide unless registered only during drags, which needs D or A anyway (F23); unproven during a foreign `DoDragDrop` |
| F. Hybrid: D always on (trigger + drag inference), A/C only to swallow while the overlay is visible, plus a watchdog | lowest | the part that can be removed (the LL hook) is installed per overlay session and torn down after; losing it degrades to "key leaks to the source" instead of "trigger dead" | as C if the hook part is in the helper | both rule families, but the hook exists for seconds at a time | moderate |

Notes on A vs C: the 50 ms p95 budget leaves ≈30 ms of headroom over the spike's warm numbers; a same-machine pipe hop is not expected to consume that, but the number is unmeasured (§6 E3). Spawn cost of the helper is off the critical path if it starts with the tray app. For B: the only benefit over C is avoiding IPC; it buys that with a second language and build chain, and does nothing for crash isolation, so it is dominated by C unless E3 shows IPC latency is a problem.

### Q6. Elevated windows / UIPI: what the hook sees and does not
- A medium-IL process cannot hook, inject into, or journal higher-IL processes (F24); reading input across integrity levels via LL hooks or Raw Input is a **UIAccess** privilege (F25). Consequence: a drag started from an elevated window (admin Explorer instance, elevated file manager, elevated app) will not expose the trigger key to our hook or Raw Input while that window is foreground. OLE drop targets across integrity levels are a separate UIPI question not covered by this research (spike manual row M12 is still pending).
- Our own injected probe keys are dropped silently when the foreground window is higher-IL (F26); callbacks for injected input carry `LLKHF_INJECTED`/`LLKHF_LOWER_IL_INJECTED` (F5), so a lower-IL process (e.g. a sandboxed browser) injecting Space can be told apart from the user.
- Never elevate, never request UIAccess (`security.md`, `windows-integration.md`); document the limitation in the product's known-limits list instead.

Requirements used: trigger→overlay < 50 ms p95 warm (budgets.md), no Administrator/UIAccess, trigger must not silently die, trigger must be swallowed only when the overlay consumed it (evaluator finding 11), Explorer's drag must not be disturbed, idle means idle, no unreviewed dependencies, hooks post and return (`windows-integration.md`).

|---|---|---|---|---|---|---|

| B. In-proc native DLL LL hook | yes | no (F2) but GC-induced loss eliminated | yes | ≈0 | **no** | yes |

## 5. Recommendation (for ADR-0003 / ADR-0005; not a decision)

1. **Do not keep the trigger's liveness on a removable hook.** Use Raw Input (`RIDEV_INPUTSINK`, keyboard + mouse, hidden window on the dedicated input thread) as the always-on detector for the trigger key/X button and for drag inference (left down + movement beyond the drag threshold). It cannot be silently removed, is Microsoft's recommended mechanism (F4), and gives the same information as the LL hooks except the swallow (F18/F19).
2. **Use the LL keyboard hook only for what Raw Input cannot do** — swallowing the trigger key while the overlay is visible — and install it **per session** (at overlay show, or at inferred drag start if the first key-down must be swallowed), on the dedicated input thread, removed at session end. A hook that lives for seconds has a small GC-overlap exposure, is re-created naturally every session, and when it dies the user loses the swallow, not the trigger.
3. **Watchdog anyway** for whatever LL hook exists: evidence-based re-install (injected marker key with `dwExtraInfo` + `LLKHF_INJECTED` check, confirmed twice; plus re-install on `WTS_SESSION_UNLOCK`/resume), always from the owning thread, never during an active session. No blind periodic re-install (chain-order and EDR side effects, Q3).
4. **GC discipline in whichever process owns input:** zero allocations in the input path (the spike's `Marshal.PtrToStructure<T>` boxes — replace with a blittable dereference as Action-Wheel does), `GCSettings.LatencyMode = SustainedLowLatency` while a session is active (F14), and log `GC.GetTotalPauseDuration()` deltas per session so the budget file gets real numbers (F15).
5. **Process placement:** decide between A and C with E3's numbers; prefer C (helper process) if its IPC p95 stays under ≈5 ms, because it also isolates the input path from engine/UI stalls and fits the worker model ADR-0005 already needs. Reject B (native DLL) under current dependency rules unless E1 shows GC pauses that no managed configuration can tame.
6. **Signing and install location are part of the robustness story:** the public EDR rules (F27-F29) are satisfied by a trusted signature and/or a `Program Files` install, independent of hook vs Raw Input. Carry this into ADR-0008 (packaging) and the threat model; on development machines with EDR, expect unsigned dev builds that install `WH_KEYBOARD_LL` from managed code to be killed, and keep a signed test build path.

## 6. The smallest experiment that settles the remaining uncertainty

One throwaway spike under `spikes/hook-robustness/` reusing the Spike 001 harness (`SendInput` choreography, Explorer-driven drag), three runs, one results table. No product code.

- **E1 — GC overlap and removal (decides A vs C and the watchdog design).** Host with the spike's `LowLevelHooks` on its dedicated thread; a background allocator producing gen0/1 churn, periodic background gen2, and a few *induced blocking* gen2 collections on a deliberately inflated heap (e.g. 200 MB of live objects) to simulate a worst case; per-callback latency measured as `Stopwatch` at callback entry minus `KBDLLHOOKSTRUCT.time` (`GetMessageTime` clock) and callback duration; GC pauses from `GC.GetTotalPauseDuration()` deltas and an EventPipe listener on `GCSuspendEEBegin/GCRestartEEEnd`; a 1 Hz injected marker key as the liveness probe. Record: distribution of callback delay, max GC pause, whether the hook was ever removed, and whether `UnhookWindowsHookEx` returns 1404 after a forced removal (one callback made to sleep 1500 ms). Acceptance: either "no pause > 100 ms in 1 h on a 200 MB heap" (A survives with a watchdog) or the numbers that justify C.
- **E2 — Raw Input during a real Explorer drag (decides the hybrid).** Register keyboard + mouse with `RIDEV_INPUTSINK` on the input thread; run the M-scenarios from Spike 001 with Explorer as source; record whether `WM_INPUT` for Space and X1 arrives while Explorer is in `DoDragDrop`, with what latency relative to the LL hook's timestamp, whether injected harness events appear (and their `hDevice`), and what an **un-swallowed** Space does to Explorer's drag (any visible effect, any change in `QueryContinueDrag` outcome). Acceptance: Space/X1 seen 20/20 cycles, latency within budget, Explorer drag unaffected.
- **E3 — Helper-process hop (decides A vs C on latency).** Minimal managed helper that owns the hooks and forwards events over a named pipe (`PipeOptions.Asynchronous`, length-prefixed frames, no JSON); 10 000 round trips, report p50/p95/p99 and the helper's idle working set; plus cold spawn time. Acceptance: p95 hop < 5 ms, idle WS < 20 MB.

Everything else in this document is either documented (§1) or does not change the decision.
