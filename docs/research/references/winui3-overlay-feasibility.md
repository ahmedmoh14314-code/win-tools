- **Subject:** WinUI 3 (Microsoft.UI.Xaml) on the Windows App SDK, used for our radial overlay: transparent, topmost, non-activating, cursor-positioned, per-monitor-DPI window that receives OLE drops from Explorer.
- **URLs:** https://github.com/microsoft/microsoft-ui-xaml · https://github.com/microsoft/WindowsAppSDK · https://learn.microsoft.com/windows/apps/windows-app-sdk/
- **License (verified):** not applicable to a feasibility review (no code reused). For the record, the WinUI source files read below carry the header "Copyright (c) Microsoft Corporation. All rights reserved. Licensed under the MIT License."
- **Source revision read:** `dxaml/xcp/dxaml/lib/DesktopWindowImpl.cpp` and `dxaml/xcp/dxaml/lib/XamlIsland_Partial.cpp` from a local scratch copy. Their git blob hashes (`1b0bc587...`, `eff62257...`) are identical to `main` of microsoft/microsoft-ui-xaml at commit `1af995b98a02d86b1951c4babe35caa269a6d569` (2026-10-19), checked with `git hash-object` against `gh api repos/microsoft/microsoft-ui-xaml/contents/...`. `dxaml/xcp/core/core/elements/XamlIslandRoot.cpp` was fetched from the same `main`.
- **Current versions (official):** Windows App SDK stable **2.5.1** (2026-09-16); 1.8 is in maintenance until 2026-09-24; 1.7 and older are out of support ([release channels](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-channels), page dated 2026-09-29).

**Classification of WinUI 3 for the overlay: REJECT for V1; INVESTIGATE (experiment E1) only if ADR-0001 wants a third candidate.** Reasons tied to our facts:
- (a) The spike already has two hosts that meet every measured requirement (spike §R-E) without any undocumented step. A WinUI overlay needs a six-step reverse-engineered recipe for transparency (AW §1.3) plus interop for non-activation, and three open rendering bugs sit in that recipe's area.
- (b) WinUI 3's drop path is a closed-source layer (`Microsoft.UI.Input.DragDrop`) with an open "elevated not supported" limitation and a fresh, unanswered "DragOver never fires" report on the current stable release. Our Win32 host is a direct `RegisterDragDrop` we control, measured at 100/100 in self mode (shell data object) and 10/10 with Explorer as the source, paths byte-exact.
- (c) Memory is unknown, but every official and semi-official hint points to "at least WPF" (spike: WPF 137 MB WS vs Win32 46 MB), and part of a WinUI window's cost lives in `dwm.exe`, where our in-process sampler would not see it (#11523).

Nothing found contradicts a spike conclusion. One finding sharpens the spike's dead-zone explanation (§6.3) and one corrects a hypothesis in AW §5 Q1 (§1, §10).

## 1. Transparent background
**Status: PARTLY.**

- **No public API, open since 2019.** [microsoft-ui-xaml#1247](https://github.com/microsoft/microsoft-ui-xaml/issues/1247) "Proposal: Borderless transparent window background support in apps using WinUI" is **open** (labels `feature proposal, area-AppWindow, team-CompInput, wpf-vs-winui-mismatch`). Duplicates are consolidated into it, e.g. [#7276](https://github.com/microsoft/microsoft-ui-xaml/issues/7276), closed 2026-06-23 by a COLLABORATOR: "Closing as a duplicate of #1247. Both request WinUI 3 support for transparent borderless windows comparable to WPF AllowsTransparency / WindowStyle=None." A MEMBER in #1247 (2023-08-22): "FWIW there is an API to do this - `IWindowPrivate::TransparentBackground(bool)`. It's just not exposed as a public API."
- **Source confirms it.** `DesktopWindowImpl::get_TransparentBackgroundImpl` / `put_TransparentBackgroundImpl` return `E_NOTIMPL` with `ERROR_WINDOW_DESKTOP_NOT_IMPLEMENTED` (DesktopWindowImpl.cpp L781-792). At creation the island is made opaque: "Turn off transparent islands by default. We'll turn them back on on a per-window/per-island basis as system backdrop brushes are used (see put_SystemBackdrop)." (L145-152). `SetXamlIslandRootBackground` (L2590-2613) calls `SetHasTransparentBackground(true)` only when a `SystemBackdrop` or backdrop brush is set: "Remove solid color background - we need transparency for system backdrop to show through."
- **The opaque fill is GDI, per theme.** `WM_ERASEBKGND` fills the client rect with `GetFrameworkTheming()->GetHwndBackground(appTheme)` (L1435-1469). Open proposal [#11134](https://github.com/microsoft/microsoft-ui-xaml/issues/11134) (community source analysis) quotes `FrameworkTheming.cpp`: `backgroundColor = (theme == Theme::Light ? 0xffffffff : 0xff000000);`. This is why AW needed a `WM_ERASEBKGND` subclass ("In Light mode that clear is white", AW §1.3).
- **SystemBackdrop is the only official hook.** [SystemBackdrop class](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.media.systembackdrop): "Base class for custom system backdrops used to render materials like Mica and Acrylic." The only derived classes are `DesktopAcrylicBackdrop` and `MicaBackdrop`. Nothing in the docs says a custom backdrop may be fully transparent; that use is an inference from the source above.
- **`TransparentTintBackdrop` is not Microsoft's.** A search restricted to learn.microsoft.com/github.com and a code search in both Microsoft repositories found no such type; the hits are the community library WinUIEx (dotMorten/WinUIEx discussion #155, issue #149). Its use is reported in [#10274](https://github.com/microsoft/microsoft-ui-xaml/issues/10274) (open): "you used to be able to create a top-level window with a TransparentTintBackdrop and the DWM non-client rendering attribute to not use rounded corners ... This used to work on Windows App SDK versions 1.5.8 or earlier. After upgrading ... (1.6.3 as of this writing), this has stopped working, and instead you get a thin border around the window".
- **`WS_EX_NOREDIRECTIONBITMAP`: not used by WinUI windows.** `DesktopWindowImpl::CreateDesktopWindow` calls `_CreateWindow(0 /* Extended Style */, ..., WS_OVERLAPPEDWINDOW | WS_VISIBLE, CW_USEDEFAULT, SW_HIDE, ...)` (L1870-1883). Open proposal [#11523](https://github.com/microsoft/microsoft-ui-xaml/issues/11523) (2026-08-13, community): "its top-level window is still created with a GDI redirection surface that the framework never meaningfully draws into. That surface costs ... a measured 7.91 MB for a 1080p window" and "`WS_EX_NOREDIRECTIONBITMAP` only takes effect at window creation, and the framework creates the window." A community comment in #1247 (2025-08-03) claims the opposite ("WinUI composition window has WS_EX_NOREDIRECTIONBITMAP ext. style"); the current source does not support it. **This corrects the premise of AW §5 Q1.**
- **Colour-key layering does not work, by design.** [#8469](https://github.com/microsoft/microsoft-ui-xaml/issues/8469), closed by a CONTRIBUTOR: "Closing this issue as by design. As noted above, WinUI renders through the Composition APIs which draw in a separate layer not impacted by the SetLayeredWindowAttributes API." (Agrees with AW: "The classic WS_EX_LAYERED colour-key trick does not work with WinUI 3 content.")
- **DesktopAcrylic on a non-activating window.** [#10570](https://github.com/microsoft/microsoft-ui-xaml/issues/10570) (closed for lack of author feedback, not fixed): "the blur effect only appears when the window is focused ... I am intentionally using the `WS_EX_NOACTIVATE` extended window style". The official [System backdrops](https://learn.microsoft.com/en-us/windows/apps/develop/ui/system-backdrops) page shows why: its controller sample sets `configurationSource.IsInputActive = args.WindowActivationState != WindowActivationState.Deactivated`, so the material follows activation. A never-activated overlay would get the fallback unless a custom `SystemBackdropConfiguration` pins `IsInputActive = true` (inference, untested).
- **Rendering bugs on transparent windows, both open:** [#8594](https://github.com/microsoft/microsoft-ui-xaml/issues/8594) "Incorrect Transparency Rendering in WinUI when HDR is Enabled" (2023-06-30, `bug, team-CompInput`): "When Windows HDR is enabled, semi-transparent controls rendered using WinUI exhibit incorrect transparency." [#11172](https://github.com/microsoft/microsoft-ui-xaml/issues/11172) "Thin white border on transparent window?" (2026-06-10, `area-Windowing, team-Core`, transferred from WindowsAppSDK by a MEMBER): "in HDR mode, the thin white border, removed or invisible. but in SDR mode, it's shown." Both citations in AW §4 item 6 are verified.

Consequence: a transparent WinUI overlay is achievable only through the AW recipe (custom transparent backdrop + `DwmEnableBlurBehindWindow` + DWM border/corner attributes + frame-bit stripping + `WM_ERASEBKGND` subclass), none of which is a documented contract, with three open rendering bugs in the same area. **REJECT as a product basis** (same conclusion as AW §1.3).

## 2. Topmost
**Status: ANSWERED, with an open bug.**
- [OverlappedPresenter.IsAlwaysOnTop](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.windowing.overlappedpresenter.isalwaysontop): "Gets or sets a value that indicates whether this window will be kept on top of other windows." Remarks: "If there is more than one window marked as always on top, the window that was last activated or interacted with will be on top." For a window that is never activated, another topmost window activated later stays above it; the product must re-assert z-order on every show (our Win32 host already uses `SetWindowPos(HWND_TOPMOST, ..., SWP_NOACTIVATE)`).
- [Manage app windows](https://learn.microsoft.com/en-us/windows/apps/develop/ui/manage-app-windows) (2026-10-13): "Set IsAlwaysOnTop to true to keep this window on top of other windows. If you call any of the AppWindow.MoveInZOrder* methods, they still take effect to change the z-order of the window even if this property is true." `CompactOverlayPresenter` "Configures an always-on-top window of a fixed size, with a 16:9 aspect ratio" (not useful for a ring).
- **Bug:** [#9990](https://github.com/microsoft/microsoft-ui-xaml/issues/9990) (open since 2024-09-14, `bug, team-Reach, team-CompInput, area-Windowing, team-Core`): "When the WinUI3 desktop window is launched, any window with the TOPMOST style of any other process will lose the TOPMOST effect, but the TOPMOST style does not disappear." A tray utility that creates its overlay at startup would disturb other apps' topmost windows if this still reproduces on 2.5.x (unverified).

## 3. Non-activating show
**Status: PARTLY.**
- [AppWindow.Show(Boolean)](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.windowing.appwindow.show): "Shows the window with an option to activate it or not." Parameter: "`true` to activate the window; otherwise, `false`." That is the whole contract. It says nothing about later clicks (that is `WS_EX_NOACTIVATE`'s job), about whether the XAML `Window` must have been `Activate()`d first, or about the first-show position. The capability arrived with 1.1 ([1.1 release notes](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-1-1): "Apps can show, minimize, or restore a window while specifying whether the window should be activated or not at the time the call is made.").
- `WS_EX_NOACTIVATE` / `WS_EX_TOOLWINDOW` have no AppWindow equivalent; interop on the HWND (`WinRT.Interop.WindowNative.GetWindowHandle`, documented in [Manage app windows](https://learn.microsoft.com/en-us/windows/apps/develop/ui/manage-app-windows)) is required. AW reports two undocumented traps: styles set before `SetPresenter` "were silently reverted", and WinUI puts `WS_DLGFRAME/WS_EX_WINDOWEDGE` back after the first show (AW §2 items 2, 4). The 1.1 release notes document related guardrails: "Windows created with AppWindow::Create will have the default Presenter guardrails in place from the start", plus a known bug when USER32 style changes and presenter switches are mixed.
- Why the first show lands at a default position (AW pitfall 4): the HWND is created with `CW_USEDEFAULT` and `WS_VISIBLE` with `SW_HIDE` as the `y` argument (DesktopWindowImpl.cpp L1870-1883), so Windows applies default placement on the first real show. Whether `Show(false)` after an early `Move` avoids AW's double `Move` is **not documented** (AW §5 Q3 stays open).
- **Side effects of never activating the XAML window:** [#10995](https://github.com/microsoft/microsoft-ui-xaml/issues/10995) (open): "When showing a modal dialog using `AppWindow.Show()` ... the underlying XAML `Window` does not appear to become activated. As a result, hover-based input such as `ToolTip` does not work until the window is manually reactivated." Plus the acrylic fallback (#10570, §1). Whether XAML `DragOver` hit-testing and visual states work in a never-activated window is **unknown**; our sector highlight during the drag depends on it.

## 4. Positioning in physical pixels at the cursor
**Status: ANSWERED.**
- [AppWindow.Move](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.windowing.appwindow.move): "Moves the window to the specified point in screen coordinates." Remarks: "Screen coordinates are relative to the upper-left corner of the screen; the coordinates of the upper-left corner are (0,0)."
- [Manage app windows](https://learn.microsoft.com/en-us/windows/apps/develop/ui/manage-app-windows): "AppWindow.Resize and AppWindow.ResizeClient take sizes in physical pixels." Its table lists `AppWindow.Resize`, `ResizeClient`, `Size`, `ClientSize` as "Physical pixels" and `Window.Bounds` as "Logical pixels". The work area is reachable via `DisplayArea` (the page's sample: `DisplayArea.GetFromWindowId(appWindow.Id, DisplayAreaFallback.Nearest)?.WorkArea`). Logical-pixel `Window.Width/Height` exist only in 2.3 Experimental A: "Don't use them in production apps."
- The spike's placement model (physical cursor point, monitor work area, clamp; spike §R-C, unit-tested) maps directly; the conversion boundary is `XamlRoot.RasterizationScale` (§5). The edge/corner design problem (cursor outside a clamped ring, spike §R-C) is framework-independent.

## 5. Per-monitor DPI
**Status: PARTLY.**
- [XamlRoot.RasterizationScale](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.xamlroot.rasterizationscale): "Gets a value that represents the number of raw (physical) pixels for each view pixel." That is the official DIP/physical bridge.
- PMv2 awareness comes from the project's `app.manifest` (AW: "`app.manifest` declares `PerMonitorV2`", from the template). No Learn page was found that states PMv2 as a WinUI guarantee; Microsoft's general guidance is to set it in the manifest ([Setting the default DPI awareness for a process](https://learn.microsoft.com/en-us/windows/win32/hidpi/setting-the-default-dpi-awareness-for-a-process)).
- Known DPI bugs in areas we would touch: [#9717](https://github.com/microsoft/microsoft-ui-xaml/issues/9717) (open) "Default drag UI tooltip is not per monitor dpi aware"; [#11129](https://github.com/microsoft/microsoft-ui-xaml/issues/11129) (open) "ItemsView crashes on DPI change (0xC000027B in Microsoft.UI.Xaml.dll)"; [#10452](https://github.com/microsoft/microsoft-ui-xaml/issues/10452) (open) "PreferredMinMaxWidthHeight APIs don't handle different DPIs well". AW's mixed-DPI trap (HWND sized for the wrong monitor before first show; AW pitfall 5) is not documented by Microsoft.
- Our M8 (second monitor / mixed DPI) is untested for every host (spike §Manual protocol); WinUI adds no evidence either way.

## 6. Receiving OLE drops that originate in Explorer
**Status: PARTLY.**

### 6.1 What is official
- [Drag and drop](https://learn.microsoft.com/en-us/windows/apps/develop/data/drag-and-drop) (2026-09-27): "Drag and drop allows data transfer between or within any kind of application, including Win32 desktop apps ... Once implemented, drag and drop works in all directions, including app-to-app, app-to-desktop, and desktop-to-app." Steps: `AllowDrop="True"`, handle `DragOver` and set `AcceptedOperation` ("Copy is the most common"), read `DataView` / `StandardDataFormats.StorageItems` in `Drop`.
- XAML-level hit-test rule: "the specified area must not have a null background, it must be able to receive pointer input, and the item cannot be dropped anywhere other than the specified area" and "Typically, a UI element has a null background by default. If you want users to be able to drop an item anywhere within your app, the app background cannot be null (set `Background="Transparent"` if the background should not be visible)."
- The receive path is the Windows App SDK input layer: the same page maps "Receive drop from the shell" to `DragDropManager.TargetRequested` / `IDropOperationTarget` (`Microsoft.UI.Input.DragDrop`). In the source, `CXamlIslandRoot` calls `GetDragDropManagerStatics(...)->GetForIsland(GetContentIsland(), &m_dragDropManager)` and handles `TargetRequested` (XamlIslandRoot.cpp L832-868). The [DragDropManager](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.input.dragdrop.dragdropmanager) page documents no OLE details (which HWND registers, how `DROPEFFECT` maps, what happens on DragLeave); that layer is not in the open microsoft-ui-xaml repository.
- Our safety rule "always return COPY, never MOVE" (spike fact 4) maps to `AcceptedOperation = DataPackageOperation.Copy`. Whether the input layer can ever report MOVE to Explorer by itself is not documented (INVESTIGATE: assert the source-side effect as the spike's self mode does).

### 6.2 Known problems
- **Elevated: unsupported, open since 2022.** [#7690](https://github.com/microsoft/microsoft-ui-xaml/issues/7690) "Drag&Drop does not work with within Elevated Apps" (open). MikeHillberg (CONTRIBUTOR, 2022-10-31): "There's a limitation currently that drag/drop isn't supported in apps running elevated". Scottj1s (MEMBER, 2023-04-17) on external content into an elevated app: "That would present the ban icon, and is a behavior of Windows." [1.1 release notes](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-1-1), Elevation, known limitations: "Elevated WinUI apps crash when dragging an element during a drag-and-drop interaction." [WindowsAppSDK#3921](https://github.com/microsoft/WindowsAppSDK/issues/3921) quotes the runtime message "Drag start failed. If this is an elevated process, drag/drop is currently not supported there" (closed as duplicate of #7690). We never run elevated (project rules); this matters only for M12 (elevated source, UIPI), which blocks every framework equally.
- **External drops silently not delivered.** [#10119](https://github.com/microsoft/microsoft-ui-xaml/issues/10119) "WinUI 3 Desktop: Drag and drop file from Explorer to app window does not work" (closed 2025-01-15 as duplicate; `bug, Regression, area-DragAndDrop`): "`Grid_DragOver()` is not being called. You just get the red cursor symbol as if drop is not allowed." The reporter fixed his case with `EnableLUA=1` ("made it work after a restart"). A new comment (2026-09-18, community) on **2.5.1**: "Even when creating a brand new, empty WinUI 3 project, dragging external files (e.g., from File Explorer) into the application window results in a persistent blocked icon ... The `DragOver` and `Drop` events are simply never fired", having ruled out a null background, Visual Studio elevation, `EnableLUA` and `DragAcceptFiles`. Unconfirmed and possibly environmental, but on the current stable release with no Microsoft response. History: [#2715](https://github.com/microsoft/microsoft-ui-xaml/issues/2715) (preview-era), 1.1 "Fixed issue where users are unable to drop an element when drag-and-drop is enabled" ([#7008](https://github.com/microsoft/microsoft-ui-xaml/issues/7008)), 1.1.1 "Fixed issue causing apps to sometimes crash during a drag and drop operation" ([#7002](https://github.com/microsoft/microsoft-ui-xaml/issues/7002)).
- **Unpackaged works in community tests:** [#8307](https://github.com/microsoft/microsoft-ui-xaml/issues/8307) (community): "I tested with an unpackaged App, Windows App SDK 1.1.0" with a GIF of a working Explorer drop; the reporter's failure was machine-specific ("Demo can run when i change my computer"). No official statement on unpackaged-specific drop behaviour was found.
- **Event args die across `await`.** [#9296](https://github.com/microsoft/microsoft-ui-xaml/issues/9296) (closed): setting `DragUIOverride` after async code throws; a CONTRIBUTOR links #8108, described as "by design", and recommends a synchronous handler ("Using a synchronous handler with `e.DataView.GetStorageItemsAsync().GetAwaiter().GetResult()` makes the problem go away"). For us: `DragOver` must be synchronous (as in the spike), and paths come through `StorageItems` -> `StorageFile.Path`, an extra WinRT hop compared with reading `CF_HDROP`. Whether `StorageItems` preserves > 260-char paths, Unicode and 3+ items exactly as our HDROP reader does (spike §R-A, unit-tested round-trip) is **not documented** (INVESTIGATE).
- WebView2 drop issues (#10142, #9650, #10576) are irrelevant unless WebView2 is used.

### 6.3 Drops over transparent pixels (the spike's dead-zone question)
**No official WinUI statement found.** What the sources imply:
- Win32 [Window Features, Layered Windows](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features): "Hit testing of a layered window is based on the shape and transparency of the window. This means that the areas of the window that are color-keyed or whose alpha value is zero will let the mouse messages through." This is the documented mechanism behind the spike's WPF observation (spike §R-E: WPF `AllowsTransparency` is a layered window; DragEnter came only when the cursor reached a painted pixel, ~335-351 ms). It upgrades the spike's explanation from inference to documented behaviour.
- A WinUI 3 top-level window is **not** layered (`_CreateWindow(0, ...)`, §1) and its transparency is a composition effect, so that rule should not apply: the OS-level target is the whole window rectangle. Prediction (unverified): DragEnter arrives immediately even over the transparent dead zone (good), **but the transparent square corners outside the ring also belong to our window**, so a release there goes to our target instead of the Explorer window visible underneath (a new hazard; in WPF the corners pass through). XAML's own rule (null background = not a drop target) would then make our target refuse the drop there, which is safe for files but swallows a drop the user aimed at Explorer.
- Community reports say a Win32 window region gives input pass-through on WinUI windows: [discussion #10746](https://github.com/microsoft/microsoft-ui-xaml/discussions/10746) and #1247 comment 3148464423 (community): "Same behaviour as WPF (passing mouse events as you wrote) can be done with Win32 regions (old method)". A circular `SetWindowRgn` is what our Win32 host already does (spike §R-E: "opaque circle"). Region + composition-rendered WinUI content + OLE hit-testing together is **untested by anyone we can cite**.

## 7. Unpackaged deployment
**Status: ANSWERED, with an official contradiction.**
- **Two options** ([Distribute an unpackaged WinUI 3 app](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/unpackage-winui-app), 2026-10-02): "Option 1: Windows App SDK runtime installer (.exe) (recommended) ... Users must run the runtime installer once." "Option 2: Self-contained deployment ... The trade-off: your output folder is significantly larger (the full runtime is included), and each app update carries the full runtime payload." Also: "Runtime dependency — The Windows App SDK runtime must be present on the user's machine. You must either bundle the runtime installer with your app, or use self-contained deployment (which significantly increases output size)."
- **Runtime installer** ([framework-dependent unpackaged deployment guide](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/deploy-unpackaged-apps)): "For apps that are packaged with external location or unpackaged, the Visual C++ Redistributable is a requirement." "If the app is running elevated and the user doing the installation has admin privileges, then the installer will register the MSIX packages system-wide ... If system-wide registration is not successful, the installation will be performed for the current user doing the installation only." Return code `0x80070005`: "System-wide install or provisioning was not possible because the app is not running elevated or the user doing the installation doesn't have admin privileges." "Experimental and preview versions of the Windows App SDK require that sideloading is enabled to install the runtime." It recommends deploying `.winmd` files "unless you're extremely concerned about size". So framework-dependent is installable per-user without elevation, but it is a second installer (MSIX packages Framework, Main, Singleton, DDLM) plus the VC++ redistributable. No official installer size found (GitHub release v2.5.1 has no attached assets).
- **Single-file: two official pages disagree, built from the same docs commit** (`b6b101756fc5a70cdab6432bdbafeb94f5637474`, both dated 2026-10-02):
  - [unpackage-winui-app](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/unpackage-winui-app#single-file-exe): "Starting with Windows App SDK 1.5, **unpackaged, self-contained** WinUI 3 apps support the .NET `PublishSingleFile` deployment model. This produces a single distributable EXE file — all dependencies are bundled into the EXE and extracted to a temp directory at first launch." Requires `EnableMsixTooling`, `IncludeAllContentForSelfExtract`, `WindowsPackageType=None` (build errors otherwise).
  - [deploy-self-contained-apps](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/self-contained-deploy/deploy-self-contained-apps): "Note that `dotnet publish` bundles managed assemblies but **cannot produce a single-file EXE** for WinUI 3 apps — the native Windows App SDK runtime dependencies must remain as separate files."
  - Practice: open [#10173](https://github.com/microsoft/microsoft-ui-xaml/issues/10173) "Published unpackaged app in Single File does not execute" (1.6.2, `area-Unpackaged`); AW: single-file "crashed on launch on every machine it was tried on" below 2.3.1, works on 2.4.0, 283.9 MB exe. Even when it works it is an extract-to-temp model. We would not ship single-file regardless; the contradiction is recorded so nobody cites one page as settled.
- **Startup cost, framework-dependent vs self-contained:** [WindowsAppSDK#4697](https://github.com/microsoft/WindowsAppSDK/issues/4697) (community measurement, 1.6): "using dynamic dependencies increases startup time by 100-300ms depending on processor speed". A MEMBER confirmed the mechanism ("WinAppSDK has its own parallel implementation that approximates the same net result ... but can't be quite as lean as the former"); closed 2025-10-21 after the reporter wrote "Impact on startup time has been reduced drastically." No official number before or after.

## 8. Idle memory and cold start
**Status: UNANSWERED (no official numbers exist that we could find).**
- The only official statement: [What's supported when migrating from UWP to WinUI 3](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/migrate-to-windows-app-sdk/what-is-supported) (2026-10-13): "As of Windows App SDK 2.0, launch speeds, RAM usage, and installation size of WinUI apps are larger/slower than seen in UWP. We're actively working to improve this." (Not re-read: the 1.2 release notes reportedly give "~7% startup performance improvement for a basic Hello World app" from trimming, a relative figure only.)
- [#8736](https://github.com/microsoft/microsoft-ui-xaml/issues/8736) (open) "WinUI3 unpackaged application memory consumption" (template app; the number is only in a screenshot). Microsoft CONTRIBUTOR (2024-04-13): "This usage is typical of a WinUI unpackaged app. We are looking at ways to reduce memory consumption by WinUI apps. I would treat this as a performance improvement goal than a bug." No figure.
- Microsoft discussion [#11096](https://github.com/microsoft/microsoft-ui-xaml/discussions/11096) "WinUI 3 Performance: A Leap Forward" (2026-05-11): File Explorer launch, WinUI portion: "Allocations 41% fewer ... Time spent in WinUI code 25% reduction"; "Some optimizations involve small or large breaking changes and will require apps to opt in." Relative and File-Explorer-specific; no absolute memory or cold-start numbers.
- **Hidden costs our in-process sampler would miss or misattribute:**
  - GDI redirection surface owned by DWM: "a measured 7.91 MB for a 1080p window ... The surface is allocated and owned by the compositor process, not by the app that owns the window. An app's own memory counters never move" ([#11523](https://github.com/microsoft/microsoft-ui-xaml/issues/11523), community measurement). For a 275x275 ring this is ~0.3 MB by the same formula, but E1 must difference `dwm.exe` anyway.
  - Hidden windows keep animating: [#12159](https://github.com/microsoft/microsoft-ui-xaml/issues/12159) (open, community): "a hidden tray popup with a single running spinner used 1.3–1.6% of a core around the clock ... The CPU is on a `dwmcorei.dll` thread (the in-process compositor), not the UI thread, so a managed profiler shows nothing." And [#12160](https://github.com/microsoft/microsoft-ui-xaml/issues/12160) (open): `Window.VisibilityChanged` "is not raised when the window is hidden or shown again". Both conflict with `performance.md` "idle means idle" unless every animation is stopped manually on hide.
  - Per-window leak: [#12210](https://github.com/microsoft/microsoft-ui-xaml/issues/12210) (open, 2026-10-08): `ExtendsContentIntoTitleBar` windows leak "~30 handles, 2–3 MB" per closed window (relevant to AW's window-per-open design).
  - Forced blocking GCs: [#12113](https://github.com/microsoft/microsoft-ui-xaml/issues/12113) (open proposal, community, with source links): WinUI requests a full blocking `GC.Collect()` from the UI-thread frame in `CCoreServices::TrackMemory` ("On every 51st call") and in `TriggerCollectionForOrphanedObjects`. A blocking GC suspends all managed threads, including a managed low-level-hook thread in the same process; this is a WinUI-specific addition to the hook-timeout risk in spike evaluator finding 5 / `input-hook-robustness.md` (inference, not measured).

## 10. What Action Wheel already answers, and what it does not
- Answers (with its own caveats, AW §1.3, §1.9, §2): the transparency recipe and its failure modes; `WS_EX_NOACTIVATE` + `Activate()` keeps focus (their claim, not measured); style-reversion and double-`Move` traps; mixed-DPI resize before show; self-contained single-file size (283.9 MB) and the < 2.3.1 crash.

## 11. Smallest experiment that answers the open questions (E1, throwaway, under `spikes/`)
Only worth running if ADR-0001 wants a third candidate; otherwise record WinUI 3 as rejected with this document as evidence.

**Setup:** one unpackaged WinUI 3 host (Windows App SDK 2.5.1, net10.0, PMv2 manifest) on the existing spike Core and harness (same `InteractionSession`, same dedicated hook thread, same JSONL fields as the Win32/WPF hosts). One pre-created `Window`, 275x275 physical px, transparent via the AW recipe, `IsAlwaysOnTop`, `WS_EX_NOACTIVATE|WS_EX_TOOLWINDOW` set after `SetPresenter`, shown with `AppWindow.Show(false)` (variant B: `Activate()` with `WS_EX_NOACTIVATE`), hidden with `AppWindow.Hide()`. Ring drawn in XAML with a `Transparent`-background dead zone; `AllowDrop` + synchronous `DragOver` returning `Copy`; `Drop` reads `StorageItems` paths. Region variants: (i) none, (ii) circular `SetWindowRgn`. Build framework-dependent and self-contained (not single-file).

**Measurements (Release, 100 cycles, same machine and harness as spike §R-E), with pass bars:**
| Metric | Spike reference | E1 pass bar |
|---|---|---|
| hook -> shown, median / max | Win32 9.6 / 18.5 ms; WPF 6.4 / 35.6 ms | median <= 15 ms, max <= 40 ms |
| hook -> first `CompositionTarget.Rendering` (proxy, as WPF) | WPF 7.2 ms median | median <= 15 ms |
| hook -> DragEnter **without cursor movement**, cursor over the transparent dead zone | Win32 15.2 ms; WPF 348.7 ms | median <= 30 ms (answers AW §5 Q1) |
| release over a transparent **corner** of the square (outside the ring), Explorer window below | WPF: passes through | (i): record whether the drop is swallowed; (ii): must reach the window below |
| drops received / paths exact (3 files: spaces, Arabic/Japanese/emoji; plus one > 260 chars) | 100/100, exact | 100/100, byte-exact including the long path |
| source-side effect (self mode) | COPY x100, MOVE x0 | COPY only |
| focus stolen | never | never; foreground HWND unchanged |
| sector highlight during DragOver on a never-activated window | n/a | follows the cursor (answers the #10995 risk) |
| first show after process start (cold) | not yet measured for any host | record; framework-dependent vs self-contained |
| idle working set / private bytes after 100 cycles + 30 s idle | Win32 45.7 / 14.3 MB; WPF 137.3 / 88.6 MB | record; **reject if WS > WPF's 137 MB** |
| `dwm.exe` private bytes delta (window created vs not) | not measured | record |
| threads; idle CPU by an external sampler, window hidden 30 s | Win32 10-14, WPF 28-34; ~0 % | ~0 % (answers the #12159 risk) |
| GDI/USER/handle counts over 100 cycles | flat | flat |
| another process's topmost window stays topmost after our startup | n/a | stays topmost (answers #9990) |
| Light theme, Dark theme, HDR on (if a display is available) | n/a | no white/black square, no border (answers #8594, #11172) |
| hook callback worst case while WinUI runs; `GC.CollectionCount(2)` delta logged | 2.75 / 4.6 ms | < 50 ms (answers the #12113 risk) |

Any single failure among "DragEnter over transparent pixels", "corner pass-through with region", "focus never stolen", "paths exact" or "WS <= WPF" is enough to reject WinUI 3 for the overlay; the other rows inform ADR-0001 only if all of those pass.
