# Reference review: other radial implementations on Windows (DragShift, Gradial, AutoHotPie)

- **Date of this review:** 2026-10-20
- **Reviewer stance:** clean-room reading of untrusted depth-1 clones in a local scratch directory; nothing was built, installed or executed, no code was copied. Short author comments are quoted as evidence only. File paths below are relative to each repository root.
- **Baseline we compare against:** `docs/research/2026-10-19-interaction-spike.md` (cited as "spike §...") and `docs/research/references/action-wheel.md` (cited as "AW §..."). This review only records evidence that is *new* relative to Action Wheel.
- **Feeds:** ADR-0001 (UI framework), ADR-0003 (activation trigger), ADR-0004 (overlay), ADR-0005 (hooks / process model), ADR-0008 (packaging), `docs/performance/budgets.md`.

## 1. DragShift (llamaboi55/DragShift)

**What was studied:** `README.md`; `dragshift/trigger.py` (whole), `dragshift/radial.py` (whole), `dragshift/glass.py` (capture, acrylic, drag-image hiding, window shaping), `dragshift/app.py` (job model, rings, startup), `dragshift/util.py`, `dragshift/convert.py` (type detection, naming, atomic save, Word automation), `dragshift/handoff.py`, `installer/DragShift.iss`, `DragShift.spec`, `demo/winkit.py`, `demo/e2e_windows.py`, `.github/workflows/e2e.yml`, `tests/`. macOS/Linux modules only skimmed.

### 1.1 Findings

| # | Topic | Evidence | What they do | Classification and reason (tied to spike facts) |
|---|---|---|---|---|
| D1 | Trigger detection | `dragshift/trigger.py` L1-5, L45, L51-95 | **No hooks at all.** A `QTimer` every 15 ms polls `GetAsyncKeyState(VK_LBUTTON / trigger / VK_ESCAPE)` and `QCursor.pos()`; it fires when the left button is held, the cursor moved >= 10 px and the trigger key is down. Author's reason: polling "needs no admin rights and can't stall the system the way a broken hook can". The timer runs for the whole process lifetime. | **REJECT as the product mechanism.** It violates performance.md "idle means idle" (about 66 wake-ups per second forever) and adds up to 15 ms of detection latency on top of the 7-20 ms hook->shown we measured (spike §R-A). It does sidestep the silent hook-removal problem (spike fact 5, evaluator finding 5), so it is a legitimate **fallback idea**: **INVESTIGATE** polling *only while* a cheaper signal says a drag may be in progress (e.g. started by the mouse hook's button-down, stopped on button-up), as a degraded mode when the keyboard hook is detected dead. Note that `GetAsyncKeyState` polling is also a classic keylogger pattern for AV heuristics (see `input-hook-robustness.md`). |
| D2 | Trigger key choice | `trigger.py` L14, L47-49; `README.md` "Settings"; `radial.py` L366, L371, L381 | Trigger is **Shift** by default, configurable to Ctrl or Alt - exactly Explorer's Move/Copy/Link modifiers. Mitigation: `setDropAction(Qt.CopyAction)` in DragEnter, DragMove and Drop, commented "never let a Shift(=move) drop delete the source". | **REJECT Shift/Ctrl/Alt as triggers; ADOPT CONCEPT forced COPY** (we already return COPY, spike fact 4). Decisive evidence is in their own test harness: `demo/e2e_windows.py` L120-121 "If an earlier failure let Windows move a file away (Shift-drop without the menu = move), put it back so one failure can't cascade", and L132 "stray copies of Explorer files dropped on the desktop". So in their CI the failure mode of a modifier trigger is **a real move of the user's file by Explorer**, not a cosmetic glitch. This is the strongest external support so far for ADR-0003's exclusion of drag modifiers. |
| D3 | False activation | `trigger.py` L16, L75-80 | Because detection is "button held + moved + Shift", it also fires on Shift+drag text selection or window moves. Mitigation: if no file `DragEnter` arrives while the cursor keeps moving, hide after ~50 ticks (~0.75 s). | **ADAPT.** Our hook-based detector has the same blind spot (it cannot know an OLE drag is in progress before DragEnter). A rule "shown but no DragEnter within N ms while the cursor moves -> hide" is cheap and testable in `InteractionSession`. N must exceed our measured worst hook->DragEnter (56 ms Win32, spike §R-A; ~350 ms WPF because of the transparent centre, spike §R-E). |
| D4 | Hide after release | `trigger.py` L69-72 | On "left button no longer down" (polled), `QTimer.singleShot(120, hide)`. The drop handler also hides on Drop. | **REJECT.** This is the exact hazard our evaluator found (spike §R-F.1, finding 1): a fixed timer after button-up can hide the overlay while the Drop is still in flight; the drop then lands on whatever is underneath - with Shift held, that is an Explorer move. Their CI passes because on an idle VM the drop arrives in < 120 ms (consistent with our 2-5 ms median, 11 ms max); nothing protects a loaded machine. Our rule (wait for Drop/DragLeave after DragEnter, grace only when no drag is inside) stands. |
| D5 | Ring contents before the drop | `radial.py` L192-206, L245-256, L358-367 | The menu is shown with "Drop here" and *speculative* glass renders for 4 and 7 petals; the real rings (Convert / Tools) are built only in `dragEnterEvent` from the data object's URLs. | **ADOPT CONCEPT.** Capability resolution needs the file list, which arrives only with `DragEnter`. The overlay must therefore have a neutral first frame and populate sectors at DragEnter. This makes hook->DragEnter latency a *UX* metric, not just a diagnostic: with our WPF transparent dead zone it was ~350 ms (sectors would stay unlabelled until the first move), with the Win32 opaque region 10-20 ms. Their hub under the cursor is painted glass, so their DragEnter arrives without movement. |
| D6 | Drop resolution | `radial.py` L325-336 (`hit`), L369-389 | Hover and drop use the same `hit()` geometry; hub (radius 50) and outside the petals -> `e.ignore()` (DROPEFFECT_NONE, nothing happens); a petal hit accepts COPY, hides, and defers the action with `singleShot(0)` "return to Explorer's drag loop immediately; do the work after". | **ADOPT CONCEPT** (same geometry for drawing and hit-testing, as spike §R-F.4; hub = safe cancel zone that refuses the drop; return from `IDropTarget::Drop` immediately because the source's UI is blocked in `DoDragDrop` until it returns). |
| D7 | Transparent pixels and fall-through | `radial.py` L100-104 (`WA_TranslucentBackground`, frameless, `Qt.Tool`, `WindowStaysOnTopHint`, `WindowDoesNotAcceptFocus`, `WA_ShowWithoutActivating`), L33-37 (400 px window, petals R_IN 60..R_OUT 158, 3.2 degree gaps) | Window is a 400x400 translucent square; only the glass is painted. | **INVESTIGATE (safety).** Our spike showed that on a per-pixel-alpha layered window, OLE treats fully transparent pixels as "not this window" (spike §R-E note). If the same holds for Qt's layered window, a drop in a petal gap or a window corner goes to the window underneath - with a Shift trigger, as an Explorer move. DragShift has no test for it (their e2e aims at petal centres). For us: never leave alpha-0 pixels inside any area where a release is plausible; measure it (§5 Q2). |
| D8 | Edge / corner placement | `radial.py` L139-144; `demo/winkit.py` L271-276 (`menu_center`); `demo/e2e_windows.py` L201-202 | Clamp to `QScreen.geometry()` (full monitor, **not** the work area, so the ring can sit over the taskbar); the e2e helper admits "near an edge its centre isn't the cursor"; the e2e choreography deliberately nudges the drag **away** from screen edges before pressing Shift. | **REJECT** the full-monitor clamp (we clamp to the work area, spike §R-C). No new solution to the "cursor outside the clamped ring" problem; their tests avoid it rather than solve it. Our §R-C design note remains open (ADR-0004). |
| D9 | Second ring / "nested" menu during a drag | `trigger.py` L73-74; `radial.py` L134 (`hub_timer` 420 ms), L338-349 (`hub_armed`) | Two rings (Convert, Tools). V1 has three operations and needs no second ring. A Shift tap would also flip Explorer's effect, so the key variant is rejected for us. |

### 1.2 Pitfalls (DragShift)
1. A modifier trigger turns any overlay failure into an Explorer **move** of the original; their test harness has code to put moved files back (D2).
2. Fixed 120 ms hide after button-up (D4) and 15 ms polling forever (D1).
3. Clamp to full monitor geometry, cursor not at ring centre near edges, edges excluded from e2e (D8).
4. Possible drop fall-through on alpha-0 pixels of a translucent Qt window (D7, unverified).
5. Screen capture plus hiding other processes' windows on every open (D10).
6. In-process parsing, extension-based typing, TOCTOU naming, Office automation (D12-D15).
7. Dependency note for anyone tempted by "it's MIT": the shipped bundle includes PyMuPDF, which is distributed under AGPL-3.0 or a commercial Artifex licence (general knowledge, not re-verified in this review). The MIT label of the repository does not describe the licence of the distributable.

### 1.3 Possible reuse (not performed)
MIT permits reuse with attribution; nothing was copied, and the Python/Qt code would not transfer to C# anyway. Concept-only candidates: the forced-COPY rule in every drop callback (D2, we already have it); "neutral first frame, sectors at DragEnter" (D5); hub as a refusing cancel zone (D6); dwell-to-switch-ring in place (D9, post-V1); disposable-desktop e2e with Explorer *and* Desktop sources and per-run source restoration (D17); per-user installer with SendTo/verb fallbacks (D18).

## 2. Gradial (longitudezero/Gradial)

**What was studied:** `README.md`, `DEVELOPMENT.md`, `Documentation/known-limitations-and-release-readiness.md`, `Documentation/milestone-1-overlay-pool-results.md`, `Documentation/milestone-1-input-recovery-results.md`, `Documentation/milestone-4-base-release-performance-results.md`, `Documentation/development.md` (sections "Gesture contract", "Edge behavior", input/tray health), `Gradial APP/Cargo.toml`, `Gradial APP/crates/gradial-app/Cargo.toml`, `.../resources/gradial.exe.manifest`, `.../src/overlay/pool.rs` (viewport builder, prewarm), `.../src/platform.rs` L440-600 and L660-700 (show path, style enforcement, subclass), `.../src/input/hooks.rs` (structure, install, heartbeat), `.github/workflows/ci.yml`. Lua plugin system ignored (out of scope).

**What it is:** Windows 11 x64-only radial launcher; hold M4/M5 (X buttons), move, release. Not a drop target: the overlay is click-through and all interaction comes from low-level hooks and Raw Input.

### 2.1 Findings

| # | Topic | Evidence | What they do | Classification and reason |
|---|---|---|---|---|
| G1 | Multi-monitor overlay model | `Documentation/milestone-1-overlay-pool-results.md` "Automated checks", "Live Windows checks"; `.../src/overlay/pool.rs` `prewarm_viewport`, `viewport_builder` | **One prewarmed hidden overlay per active display**, routed by signed monitor coordinates (negative coordinates and nearest-monitor fallback unit-tested). On `WM_DISPLAYCHANGE`, DPI change or work-area change the active invocation is **cancelled** (`DisplayTopologyChange`) and the pool is rebuilt with a new generation. Verified live on two 96-DPI displays only. | **ADOPT CONCEPT.** It removes the "HWND created/sized for the wrong monitor" failure Action Wheel works around per open (AW §1.3, pitfall 5) and gives each overlay a fixed DPI. Cost: one hidden window (and, in their case, one GPU surface) per monitor. Our spike used one pre-created window on one monitor (M8 untested); this is the design to spike on a mixed-DPI rig. Cancelling the gesture on topology change is the safe default for us too (an in-flight drop must then see DragLeave, not a hidden window - our §R-F.1 rule applies). |
| G2 | Shown is not painted | `milestone-1-overlay-pool-results.md` "Native repaint wake revision" | A directly shown overlay "could remain asleep until release": logs showed first frames **109-2,085 ms** after activation, painted only because the release path invalidated the window. Directly relevant to any WinUI 3 / composition-based overlay, which is also frame-driven. |

Our raw Win32 host owns its styles, so this is cheap insurance, not a required mechanism. |
| G5 | Show path | `platform.rs` `position_and_show_window`: `SetWindowPos(HWND_TOPMOST, ..., SWP_NOSIZE | SWP_NOACTIVATE | SWP_SHOWWINDOW)`, `ShowWindow(SW_SHOWNOACTIVATE)`, then invalidate | Physical-pixel positioning of a prewarmed window, no activation. | **Confirms** spike fact 6 and our "focus stolen: never" result; nothing to change. |
| G6 | Edge / corner handling ("edge assist") | `DEVELOPMENT.md` L96-102; `Documentation/development.md` "Edge behavior" and input section ("In edge-assist mode, low-level movement is suppressed so the system cursor remains at activation-down; raw mouse deltas accumulate into a virtual gesture pointer") | If the ring centred at the press point would clip the work area, they inset the ring, **swallow `WM_MOUSEMOVE` in the LL hook** so the real cursor stays put, and drive selection from Raw Input deltas through a virtual pointer drawn inside the ring. ### 2.2 Pitfalls (Gradial)
1. First frame silently delayed by up to ~2 s because a shown window was not invalidated (G2).
2. Framework resets extended styles; must be verified after set (G4).
3. GPU-backed transparent overlay: ~157 MiB idle WS, and invisible to PresentMon (G10, G11).
4. Heartbeat proves thread responsiveness, not hook presence (G9).
5. All display/DPI evidence physically limited to 96 DPI (G12).
6. Edge assist depends on swallowing mouse moves; incompatible with OLE drops as designed (G6).

### 2.3 Possible reuse (not performed)
MIT; Rust code does not transfer to C#. Concept-only: per-monitor prewarmed overlay pool with cancel-and-rebuild on topology/DPI/work-area change (G1); invalidate-on-show and frames only while animating (G2); bounded fail-open input queue (G8); re-registration on resume/unlock/`TaskbarCreated` (G9); debug-only fault-injection messages (G13); the five-state evidence vocabulary (G12); manifest shape (G14).

## 4. Excluded projects: what was still worth noting

- **RadialDock** (Apache-2.0, `7b3015a`, PySide6/QML). Opens with **Ctrl+Space via `RegisterHotKey`** (`src/radialdock/win_hotkey.py` L192) or an X-button through `WH_MOUSE_LL` on the Qt thread (L213-236, no dedicated thread); a QML `DropArea` on the ring accepts external drops for pinning (`ui/Main.qml` L663-683); clamping assumes a screen origin of (0,0) and ignores the work area (`ui/Main.qml` L103-136). One idea for ADR-0003, **INVESTIGATE**: `RegisterHotKey` (no keyboard hook, so no hook timeout and no keylogger-style hook heuristics) registered **only while a drag is in progress** (armed by the mouse hook on button-down + threshold, unregistered on button-up). While registered the key is consumed system-wide, so the window must be short; whether `WM_HOTKEY` reaches our thread promptly during Explorer's `DoDragDrop`, and whether plain Space without modifiers can be registered, must be measured, not assumed. Separate caution for the Ctrl+Space candidate: Ctrl+Space is a common IME toggle for Chinese input methods (general knowledge, not verified here), so it may collide for some users.
- **rovyl** (GPL-3.0, `5c4a579`, Electron). Concepts only; no code may be reused. (1) The mouse hook lives in a **helper process** (`backend/mouse-blocker.ps1`, C# compiled at runtime by PowerShell `Add-Type`); `backend/electron-main.js` ~L1652-1660 records that the helper can die unnoticed and that the armed trigger command is now replayed onto a fresh helper - relevant to ADR-0005's "where does the hook live" question. (2) Issue #3: the `WH_MOUSE_LL` hook was evicted "during the heavy first-run Start Menu scan / icon extraction" and never re-installed. (3) `electron-main.js` ~L622-640: Chromium marks a hidden/shown transparent layered window as occluded and shows "the old texture or a black frame" on the next show; L1065-1072 a 200 ms "stabilization delay" for the transparent compositor. Electron-specific, but another instance of "a composited transparent overlay can present a stale frame on show" (cf. Action Wheel's close flash, AW pitfall 6; Gradial G2).

### 5.2 Does anything contradict the spike?
No measured spike conclusion is contradicted. Three points sharpen or qualify it:
1. **DragShift works with the choices we rejected** (Shift trigger, 120 ms hide timer, polling) and passes CI. That is consistent with our idle-machine numbers (release->Drop median 2-5 ms) and does not refute our rules; their own harness code shows the destructive failure mode (Explorer moves the file) that our rules prevent.
2. **"Native is lean" is not a safe assumption.** Gradial (native Rust, GPU overlay) idles at 157 MiB WS, above our WPF host. Our R-E memory gap is better explained by GDI vs GPU rendering than by managed vs native; this matters for ADR-0001/0004 and for WinUI 3.
3. **Our budget's ETW measurement plan may not work** for a transparent overlay (Gradial G11). Until a composition-level method is proven, "first paint" stays a proxy (as spike §Method already states).

### 5.3 Open questions and the smallest experiment for each
1. **Q1 Hub painting vs DragEnter latency.** In the WPF host, give the dead-zone centre alpha >= 1 (visually transparent) and re-run the R-E scenario: does hook->DragEnter drop from ~350 ms to the Win32 ~15 ms? Decides whether "transparent dead zone" is a constraint or just a pixel value.
2. **Q2 Fall-through on alpha-0 pixels (safety).** Self mode with the shell drop source: release on an alpha-0 pixel *inside* the overlay rectangle (WPF host) with a second drop-target window underneath; record which window gets Drop and the effect. Expected (from spike §R-E): the window underneath. If so, the product overlay must have no alpha-0 pixels inside its drop-relevant area.
3. **Q3 Displayed-frame measurement.** Run PresentMon and a WPR trace with DWM providers during the Win32 and WPF hosts' 100-cycle runs; if neither shows overlay presents, prototype a Windows Graphics Capture probe that timestamps the first composed frame containing the ring at the cursor. Owed by `budgets.md`.
4. **Q4 Per-monitor pool on mixed DPI (M8).** Two monitors at different scales: one prewarmed overlay per monitor vs one moved overlay; measure hook->first paint and correct size on first show, and cancel behaviour on `WM_DISPLAYCHANGE` during a live drag.
5. **Q5 Screen-share visibility of the idle overlay.** With the overlay prewarmed and hidden, capture the display with Windows Graphics Capture (or OBS/Teams); look for artefacts (AutoHotPie #115).
6. **Q6 No-DragEnter timeout.** Add "shown, cursor moving, no DragEnter within N ms -> hide" to `InteractionSession` tests; choose N from measured DragEnter latency (D3).
7. **Q7 RegisterHotKey armed only during a drag** (RadialDock idea): latency of `WM_HOTKEY` during an Explorer drag, whether plain Space registers, and whether the key leaks to the foreground app.
8. **Q8 Disposable-desktop harness.** Before more Explorer/Desktop runs (spike incident 22051A, M2), move them to Windows Sandbox or a VM, following DragShift's pattern (D17), and keep at least one Windows 11 client run.
