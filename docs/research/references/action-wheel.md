# Reference review: Action Wheel (cmm-cmm/Action-Wheel)

- **URL:** https://github.com/cmm-cmm/Action-Wheel
- **Clone studied:** depth-1, commit `da021af15e6d8e82d57319b7f32c36126edea6db` ("Bump version to 2.8.0", 2026-08-25), read-only in a local scratch directory; nothing was built or executed.
- **License (verified from `LICENSE.txt` in the clone):** MIT, "Copyright (c) 2026 Minh Pham". Bundled font `Assets/Fonts/CaskaydiaCoveNerdFontPropo-Regular.ttf` is OFL-1.1 (`Assets/Fonts/Licenses/`). GitHub metadata agrees (`license.spdx_id = MIT`).
- **Project reality check (GitHub API, 2026-10-20):** 1 star, 0 forks, 0 issues (open or closed), created 2026-08-10, last push 2026-08-25, seven tagged releases v2.2.0 -> v2.8.0 in 15 days, single maintainer, no CI workflow. So: a well-commented single-author codebase, not a battle-tested product. There is no issue tracker evidence; every "pitfall" below comes from the author's own comments and `Doc/PROJECT-AUDIT-2026-08-25.md` (a Vietnamese-language audit, 7.5/10 self-score).
- **What it is:** WinUI 3 (.NET 10, `net10.0-windows10.0.19041.0`, `TargetPlatformMinVersion 10.0.17763.0`) radial launcher: middle mouse button (or chord / X buttons / Ctrl+Alt+Space) opens an 8+1 button ring at the cursor; buttons send shortcuts, launch programs, run built-in Windows functions or open a "group" satellite ring. **It does not do OLE drag-and-drop at all** (`grep AllowDrop` finds nothing), so it answers none of our drop-related questions.
- **Dependencies (`Action Wheel.csproj`):** `Microsoft.WindowsAppSDK 2.4.0` (README and CONTRIBUTING still say 2.3.1 - drift), `Microsoft.Windows.SDK.BuildTools 10.0.28000.2526`. Nothing else. `app.manifest` declares `PerMonitorV2`.
- **Size:** ~17 k lines incl. XAML; biggest files `Overlay/RadialMenu.xaml.cs` (1553), `Settings/SettingsWindow.xaml.cs` (1140), `ViewModels/SettingsViewModel.cs` (1013).
- **Date of this review:** 2026-10-20. Our evidence baseline: `docs/research/2026-10-19-interaction-spike.md` (cited as "spike §...").

## 1. Findings by topic

### 1.1 Module boundaries / Core separation
| Evidence | What they do | Classification |
|---|---|---|
| `ActionWheel.Core/ActionWheel.Core.csproj` (plain `net10.0`, `ImplicitUsings` off), `Action Wheel.csproj` `<Compile Remove="ActionWheel.Core\**">` | Business logic in a separate assembly that **cannot** reference WinUI or user32; the compiler enforces the layer. Core holds config, validation, `RingGeometry` (clamping + gesture angle), `ChordGate` (hook swallow decisions), `AtomicFile`, backup, profiles. | **ADOPT CONCEPT** - we already do this in the spike (`TriggerDetector`, `InteractionSession` are pure and unit-tested). Keep the rule "pure geometry/state machine in a no-Win32 assembly" when the product solution is created. |
| `Services/LauncherService.cs` | One service owns hooks + watcher + menu lifetime + gesture state + profile switching + reload (563 lines, static-event wiring to `ActionDispatcher`). | **REJECT** as a shape: this is the "service that contains the application" our architecture rules forbid. Split: hook host, session state machine, overlay presenter. |
| `Services/ActionDispatcher.cs` static class with static events | Dispatch via static events; `LauncherService.Dispose` must unsubscribe or leak. | **REJECT** (static events). |

### 1.2 Low-level hooks (`Services/MouseHook.cs`, `Services/KeyboardHook.cs`, `Services/LauncherService.cs`)
| Aspect | Evidence | Classification / comparison with spike |
|---|---|---|
| Thread | `SetWindowsHookEx(WH_MOUSE_LL, _proc, GetModuleHandle(null), 0)` is called from `LauncherService.Start()` on the **WinUI UI thread**; no dedicated hook thread. Their own comment (`CheckHookHealth`): "Reinstall both hooks because they share the same UI-thread timeout exposure." | **REJECT.** Spike fact 5 and Microsoft's guidance: hook on a dedicated pumping thread. Their UI thread also runs the 186 ms opening storyboard, SVG decoding and config reload; any stall > `LowLevelHooksTimeout` silently removes the hook. Our spike measured hook worst case 2.75/4.6 ms on a dedicated thread. |
| Callback cost | `ReadEvent` is an `unsafe` pointer dereference of `MSLLHOOKSTRUCT` ("Marshal.PtrToStructure boxes - 48 bytes and 20 ns per call ... 6 to 48 KB/s of Gen0 garbage inside the callback Windows times"); `AllowUnsafeBlocks` exists only for this. Cursor position read from `lParam`, never `GetCursorPos`. `TrackMovement` flag so `WM_MOUSEMOVE` does nothing unless a gesture is active. "Code reachable from a hook callback must never perform disk I/O." | **ADOPT CONCEPT** (allocation-free, no I/O, no work on moves). Anti-copy: problem = GC pause inside the timed callback; we have it (evaluator finding 5 "hook removal during GC pauses"); alternatives = `Unsafe.Read`/`Marshal.PtrToStructure` + measuring; evidence = their measurement claim, Gradial's 190 us max callback (see other-radial-implementations.md); complexity trivial; license: concept only. Our spike should add an allocation counter per callback before ADR-0005. |
| Exceptions | `HookCallback` wraps everything in `try/catch` ("a managed exception crossing back into a native frame makes the CLR fail fast"). | **ADOPT CONCEPT** (we must never let an exception leave the hook proc; log once, pass through). |
| Own-input marker | `InputInjection.Marker` 0x4152494E in `dwExtraInfo`; hook ignores its own `SendInput`. | **ADAPT** - only relevant if we ever synthesize input (we do not plan to). Note for the harness: our `SendInput` injection has no marker, so our hook sees it exactly like hardware (correct for testing). |
| Swallowing | Trigger button DOWN **and** UP are swallowed; `ChordGate` keeps first-button down/up balanced (audit F-01 was exactly an unbalanced swallow that left apps thinking a button was held; fixed in `ChordGate` remarks). Esc swallowed only when a menu was open (`EscapePressed` returns bool). Emergency `Ctrl+Alt+Space` swallows the Space key-up too. | **ADAPT.** Our product rule (spike evaluator finding 11): swallow only when the overlay consumed the key. Their balanced-pair discipline is the right detail if we ever swallow Space: swallow the matching key-up as well, otherwise the foreground app sees an orphan WM_KEYUP. |
| Failure detection / reinstall | `LauncherService.CheckHookHealth`: `DispatcherQueueTimer` every 5 s compares `GetCursorPos` movement with `MouseHook.LastCallbackTick`; "cursor moved but callback did not advance" => `ReinstallHooks()` (Stop both, Start both, all-or-nothing). Install is all-or-nothing too: "a mouse hook without a keyboard hook gives a menu that Esc silently will not close, and a keyboard hook without a mouse hook swallows Esc system-wide". `GetModuleHandle(null)` instead of `Process.MainModule` because the latter fails in a single-file publish. The reinstall reason is not recorded anywhere (no logging by policy). | **ADOPT CONCEPT** for liveness probe + all-or-nothing install. Anti-copy: problem = Windows removes slow LL hooks silently and exposes no query; do we have it = yes (ADR-0005 open item); alternatives = Raw Input (Microsoft's own recommendation, spike fact 5), periodic unconditional re-register, `WH_MOUSE_LL` + `WH_KEYBOARD_LL` cross-check; evidence = rovyl issue #3 and AutoHotPie #39 are real-world reports of exactly this silent death; complexity = ~40 lines + a test that simulates a stale tick; license = concept only. A 5 s cadence with a "cursor moved" probe cannot detect a dead **keyboard** hook; we need a keyboard-side probe or re-register both on any doubt. |
| Locked session | `TryGetCursorPosition` returns false when `GetCursorPos` fails ("on a locked or switched-out session it does ... put the ring in the top-left corner"). | **ADOPT CONCEPT** (never default to (0,0)). |

### 1.3 Overlay lifecycle, focus, positioning, DPI (`Overlay/RadialMenu.xaml.cs`, `ActionWheel.Core/RingGeometry.cs`)
| Aspect | Evidence | Classification / comparison |
|---|---|---|
| Pre-created vs on demand | **On demand, a new `RadialMenu : Window` per open** (`LauncherService.OpenMenuAt` -> `new RadialMenu(...)`; `CloseMenu()` = `ShowWindow(SW_HIDE)` then WinUI `Close()`). Author measured `InitializeWindow` 52 ms -> ~7.5 ms after deleting `AppWindow.TitleBar` and presenter configuration (46 ms "achieving nothing measurable"); claims "click-to-first-pixel is only ~15 ms" (method not stated; no cold-start number; no memory numbers anywhere). | **INVESTIGATE / lean REJECT.** Our spike shows/hides one pre-created window and gets hook->shown medians 9.6 ms (Win32) / 6.4 ms (WPF) warm (spike §R-E); a window-per-open design pays XAML tree construction, backdrop connection and DWM registration every time and makes the "first open after launch" cost invisible. If WinUI 3 is ever spiked, measure both strategies; their 7 ms is the floor for construction alone. |
| Non-activating | `SetExtendedWindowStyle`: `GetWindowLong/SetWindowLong(GWL_EXSTYLE) |= WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`, then `SetWindowPos(HWND_TOPMOST ... SWP_NOACTIVATE)`. Pitfall in comments: "The presenter has to be attached before SetExtendedWindowStyle runs: while it was being configured before `SetPresenter`, the `SetWindowLong` calls were silently reverted." Showing is done with WinUI `Activate()` (which, with `WS_EX_NOACTIVATE` set, shows without activation), **not** `AppWindow.Show(false)`. Dismissal on outside click comes from the mouse hook (`AnyButtonDown` + `ContainsScreenPoint`), because "the menu window is WS_EX_NOACTIVATE, so it never gets a deactivated notification". | **ADAPT.** Matches spike fact 6 and our result "focus stolen: never". The ordering trap (style reverted until the presenter is attached, and `RemoveWindowFrame` must run **again after** the first show because "WinUI puts WS_DLGFRAME/WS_EX_WINDOWEDGE back") is WinUI-specific and is exactly the kind of undocumented behaviour that argues against WinUI 3 for the overlay (see winui3-overlay-feasibility.md). |
| Cursor-relative positioning | `ShowAtPosition`: `RefreshDpiForTarget` (GetDpiForMonitor on the monitor under the cursor, resize if the scale differs from the one cached at HWND creation), `GetMonitorWorkArea` (MonitorFromPoint/GetMonitorInfo `rcWork`), `RingGeometry.ClampOrigin` in **physical pixels**, then `Move`, `Activate()`, `Move` again ("the first Activate() is when the window is actually shown, and Win32 applies the default position (CW_USEDEFAULT/cascade) ... overwriting the earlier Move"). | **ADOPT CONCEPT** for the mixed-DPI re-read before show ("a new top-level window is placed by Windows before anyone has told it where it is going", so the HWND can be sized for the wrong monitor). Our spike could not test M8 (second monitor/different DPI); this is the failure mode to design for. Double-Move is a WinUI artefact: **N/A** for Win32/WPF. |
| Edge/monitor clamping | `RingGeometry.ClampOrigin`: bottom/right clamp first, then top/left, so an oversize ring pins to the top-left "the centre button, the one under the cursor, stays reachable". Unit-testable record structs `ScreenRect`/`ScreenPoint`. Hit-test for "inside the menu" is the whole square window (`RingGeometry.Contains`), not the ring. | **ADAPT.** Same clamping as our spike (§R-C) and the same unsolved consequence: near an edge the cursor is no longer at the ring centre and the gesture origin stays at the press point (`_gestureOrigin`), so a flick near a corner points at a button that is drawn somewhere else. They did not solve it; Gradial did (edge assist, see other-radial-implementations.md). Our §R-C design note stands. |
| DPI | `GetDpiForWindow` at creation, `RingGeometry.ScaleFromDpi`, XAML in DIPs, `AppWindow.Resize/Move` in physical px ("at 125%/150% failing to multiply by this factor leaves the physical window smaller than the XAML content, clipping the menu's edge"). | **ADOPT CONCEPT** (one coordinate space per layer, convert at the boundary). Our spike already keeps hit-testing in the drawing coordinate space (§R-F.4). |
| Transparency | `ApplyTrueTransparency`: (1) custom `TransparentSystemBackdrop : SystemBackdrop` hands the window a `Windows.UI.Composition` colour brush `Transparent` (needs its own `Windows.System.DispatcherQueue`); (2) `DwmEnableBlurBehindWindow(fEnable, hRgnBlur = null)` ("a zero-area region is not equivalent"); (3) `DWMWA_BORDER_COLOR = DWMWA_COLOR_NONE`; (4) `DWMWCP_DONOTROUND`; (5) strip `WS_CAPTION|WS_BORDER|WS_DLGFRAME|WS_THICKFRAME` and `WS_EX_WINDOWEDGE|CLIENTEDGE|STATICEDGE|DLGMODALFRAME` with `&= ~` ("overwriting GWL_STYLE wholesale drops WS_CLIPCHILDREN/WS_CLIPSIBLINGS, which is what made the menu render blurry"); (6) `SetWindowSubclass` to answer `WM_ERASEBKGND` with a black `FillRect` ("WinUI clears the native client surface with its theme background ... In Light mode that clear is white and remains visible through transparent XAML pixels"). README: "Drop either [backdrop or blur-behind] and the menu renders as a solid black square. The classic WS_EX_LAYERED colour-key trick does not work with WinUI 3 content." Close flash: "for at least one frame before the HWND is actually destroyed the swap chain reverts to its opaque default - black" => `SW_HIDE` before `Close()`. | **REJECT as a product basis; INVESTIGATE only inside a WinUI spike.** Six undocumented steps whose interaction is the author's reverse engineering (the WinUI source confirms the mechanism: `DesktopWindowImpl::SetXamlIslandRootBackground` calls `SetHasTransparentBackground(true)` only when a `SystemBackdrop` is set, and the `TransparentBackground` property itself is `E_NOTIMPL` - see winui3-overlay-feasibility.md). Our Win32 host needs none of this (opaque circular region) and our WPF host needs only `AllowsTransparency`. |
| Hit-testing of transparent pixels | Not applicable to them (no OLE), but relevant: their outside-click test is the full square window, which implies transparent XAML pixels still belong to the HWND for input. | **INVESTIGATE** in any WinUI spike: our WPF layered window's transparent centre made OLE wait ~335 ms for DragEnter (spike §R-E note). A DirectComposition (`WS_EX_NOREDIRECTIONBITMAP`) WinUI window probably hit-tests as opaque, which would actually *help* DragEnter latency. Unverified. |
| Shadows | `Overlay/ButtonShadow.cs`: composition `DropShadow` with a circular `CompositionVisualSurface` mask ("ThemeShadow is cast onto shadow receivers elsewhere in the tree, and the overlay is fully transparent - there is nothing behind the buttons to receive anything"); masks cached per compositor, capped at 32. | **N/A** unless WinUI. Good note: on a transparent overlay nothing "receives" a system shadow. |
| Animation | `Overlay/RingOpenAnimation.cs`: seven presets, only `Opacity` + `RenderTransform` ("independent animations ... composition runs them off the UI thread"); budget 200 ms; stagger retuned 400 ms -> 186 ms "most of how slow the menu felt. Click-to-first-pixel is only ~15 ms, so the animation, not the code, is what the user is waiting for." Close can land mid-storyboard; `_closed` guard before `UpdateLayout`. | **ADOPT CONCEPT**: the user-perceived latency budget must include the animation; keep any entrance animation well under our hook->paint budget and never block the drop on it. For a *drop* target an entrance animation must not move the hit regions (they animate buttons from elsewhere - fine for clicks, wrong for drops). |

### 1.4 Radial hit testing, gesture, nested/group radials
| Aspect | Evidence | Classification |
|---|---|---|
| Click path | Real WinUI `Button`s; `RootGrid_PointerPressed` walks `VisualTreeHelper.GetParent` to decide "on a button or not" ("used to compute the distance to each button's centre by hand ... drifted the moment the style changed"). | **ADAPT**: hit regions must be derived from the same geometry that draws them (our §R-F.4 rounding lesson). |
| Flick gesture | `RingGeometry.TagForDirection(dx, dy)`: 28 px dead zone, `atan2`, round to nearest 45 degrees, measured from the **press point**, evaluated in the hook thread; UI hop only when the tag changes. | **ADAPT**. Our sectors are measured from the ring centre; with OLE the cursor is the drag point, so ring-centre geometry is correct for us. The "only cross threads when the result changes" rule is good. |
| Boundary | Rounding to nearest eighth puts the 0/1 boundary at 22.5 degrees - no explicit boundary rule. | Our §R-F.4 note is stronger (avoid exact boundaries); keep ours. |
| Hold action | 450 ms `DispatcherQueueTimer` + `ProgressRing`; fires pre-emptively because "WinUI's Button raises Click on release regardless of how long the press lasted". | **N/A** (no hold semantics in a drop). |
| Groups (nested radial) | `BuildGroupButtons`: satellites on a concentric outer ring (`OrbitRadius + ButtonSize + 24`), fanned 0,+1,-1,+2,-2 from the parent's angle with an angular step `2*asin((size+gap)/(2r))` so edge gaps stay constant regardless of radius ("reusing the main ring's 45 degree slot spacing put satellites much further apart"); one group open at a time; window sized at construction for the largest possible ring ("Resizing an already-shown, already-positioned overlay mid-gesture is the kind of thing ... to avoid"); children cannot nest (`ActionItem` "A child cannot itself be a group"). | **ADOPT CONCEPT** for the geometry (chord-based angular step; pre-size for the largest state; one level only). For us a second level is YAGNI in V1 (Convert/Compress/Resize only), but the "never resize the shown window during the gesture" rule applies to our ring too. |

| Aspect | Evidence | Classification |
|---|---|---|

| Startup | `Services/StartupManager.cs` + `Core/StartupCommand.cs`: HKCU `Run` key, path always quoted, `Matches()` treats a stale entry pointing elsewhere as "not enabled"; re-read on every menu open because Windows' Startup Apps page can disable it. | **ADOPT CONCEPT** (no elevation, no scheduled task, quoted path, stale-entry detection). |

### 1.6 Configuration architecture and corruption recovery
| Aspect | Evidence | Classification |
|---|---|---|
| Parse | `JsonDocument`, no `JsonSerializer<T>` ("needs no reflection, so enabling PublishTrimmed later can't silently break the config"). | **ADOPT CONCEPT** (or source-generated `JsonSerializerContext`, which is the .NET-native way to get the same guarantee). |
| Locations | Portable copy next to the exe shadows `%LOCALAPPDATA%` **completely, even when invalid** ("the running config and the one any edit would actually land in were two different files, silently"). | **ADAPT** (single location for V1; if portable mode ever exists, apply the "one effective file" rule). |
| Rejection | `ConfigStatus.Rejected`: defaults in memory, **file left untouched**, error + path surfaced in the main window, `RestoreBackup` validates the `.bak` first, keeps the broken file as `.invalid`. | **ADOPT CONCEPT**. ### 1.8 Performance choices (claims, not independently verified)
- Overlay build 52 ms -> 1.5 ms style work + ~7 ms total after removing TitleBar/presenter calls (comment in `InitializeWindow`); `OnLaunched` "already measured at 185 ms" (comment in `App.CheckForUpdatesAsync`); opening animation 186 ms; "click-to-first-pixel ~15 ms".
- No memory, idle CPU, cold-start or leak numbers anywhere in the repo. The audit measured only build/publish facts (self-contained exe 283.9 MB).
- `IconFactory` caches decoded SVG/raster (`MaxCachedImages`); tinted hover icons built lazily on first hover ("ApplyActions runs on the path that opens the ring - where the whole budget is about 18 ms").
- `OnActionInvoked` sleeps 40 ms before `SendInput` because WinUI "teardown can continue in the compositor after the UI queue is empty" - a timing hack of the kind our evaluator rejected for the drop path (spike §R-F.1). **N/A** for drops, but it is a signal about WinUI window teardown determinism.

### 1.10 Testing strategy
- No test project ("deliberately out of scope so far", `CONTRIBUTING.md`); three console "check" programs under `Tools/` (`RoundTripCheck`, `ChordGateCheck`, `ConfigBackupCheck`) wired into `Build.ps1 -Task All`; `Verify-Bindings.ps1` statically checks every classic `{Binding}` path because "`DebugSettings.BindingFailed` does not fire (measured ...)"; `VerifyVersionSync` because `Package.appxmanifest` cannot inherit `<Version>` and drifted (2.4.0.0 vs 2.7.0). Everything about hooks, overlay, focus, DPI, multi-monitor is manual and unrecorded.
- **REJECT** as a model (our `testing.md` requires tests as specification). **ADOPT CONCEPT**: the "verify the thing the compiler cannot" scripts (binding paths, version sync, package smoke) are cheap guards worth having in whatever form fits our stack.

## 2. Pitfalls stated by the author (consolidated)
1. Transparency needs *both* a transparent `SystemBackdrop` and `DwmEnableBlurBehindWindow`; either alone = solid black square; `WS_EX_LAYERED` colour-key does not work with WinUI 3 content (README "How it works"; `RadialMenu.ApplyTrueTransparency`).
2. `SetWindowLong` style changes are silently reverted until `AppWindow.SetPresenter` has run; frame bits must be stripped again after the first show (`RemoveWindowFrame` remarks).
3. `AppWindow.TitleBar` and presenter configuration cost 46 of 52 ms per overlay creation and changed nothing visible (`InitializeWindow` remarks).
4. First `Activate()` applies the default window position; `Move` must be repeated after it (`ShowAtPosition`).
5. A new HWND can be created on the wrong monitor in a mixed-DPI setup; re-read DPI for the target point before showing (`RefreshDpiForTarget`).
6. Closing a transparent WinUI window flashes black for a frame unless `SW_HIDE` runs before `Close()` (`CloseMenu` remarks).
7. WinUI `Button` default template leaves hover colours stuck; `ButtonBase` marks pointer events handled, so `+=` handlers never run (`AddHandler(..., handledEventsToo: true)`); `ThemeShadow` renders nothing on a transparent window.
8. `Marshal.PtrToStructure` allocates inside the LL hook callback; the hook thread shares the UI thread's timeout exposure; Windows exposes no query for hook liveness.
9. `Process.MainModule.ModuleName` fails in a single-file publish; use `GetModuleHandle(null)`.
10. Single-file WinUI 3 publish crashed (0xc000027b) with Windows App SDK < 2.3.1; renaming the exe breaks `resources.pri`; `EnableMsixTooling` must be on only while publishing; self-contained output 250-300 MB; trimming is incompatible with classic `{Binding}`.
11. `GetCursorPos` fails on a locked/switched-out session.
12. `TrackPopupMenuEx` requires `SetForegroundWindow` + `WM_NULL`; message-only windows are excluded from broadcasts; a failed `RegisterWindowMessage` returns 0 == `WM_NULL`.
13. A portable config next to the exe shadows the user config even when invalid; `FileSystemWatcher` sees truncate-then-write and temp-then-rename saves; debounce or you reload a zero-byte file.
14. `DebugSettings.BindingFailed` never fires in WinUI 3 (measured by them).
15. Audit F-01: swallowing the chord's first button-up desynchronised the app underneath; F-02: backup restore is not transactional.
16. Documentation drift inside the repo: `AGENTS.md` references an agent instruction file, `doc/FIX-DEBUG-DEPLOYMENT.md` and `Build-Publish.ps1`, none of which exist in the clone; README says WASDK 2.3.1, csproj says 2.4.0.

## 3. Comparison with our spike (`docs/research/2026-10-19-interaction-spike.md`)
| Topic | Action Wheel | Our spike | Verdict |
|---|---|---|---|
| Hook thread | UI thread | dedicated thread, worst case 2.75/4.6 ms | Ours is the documented-safe design; add their liveness probe. |
| Overlay creation | new window per open, ~7 ms + XAML | pre-created, show/hide, 9.6 / 6.4 ms hook->shown medians | Comparable warm numbers; theirs hides cold cost. |
| Focus | `WS_EX_NOACTIVATE` + `Activate()` | `WS_EX_NOACTIVATE` + `SW_SHOWNA`, "focus stolen: never" over 100 cycles | Same mechanism, ours measured. |
| Edge clamping | pin to work area, cursor may be off-centre | same, with the design note in §R-C | Neither solves it; Gradial's edge assist is the only reference that does, and it is incompatible with OLE (see other doc). |
| Transparency | 6-step undocumented WinUI recipe | opaque circular region (Win32) / `AllowsTransparency` (WPF) | Ours needs no hack; theirs is a reason to prefer Win32 or WPF for the overlay. |
| Drops | none | Explorer -> CF_HDROP paths 100 % over 100+ cycles | No contradiction, no help. |
| Hide timing after release | n/a (click, not drop) | must wait for OLE Drop/DragLeave (§R-F.1) | Their 40 ms post-close sleep before `SendInput` is the same class of timing hack we rejected. |
| Memory / idle | unmeasured; self-contained 284 MB on disk | Win32 45 MB WS, WPF 137 MB WS, idle CPU ~0 | WinUI 3 expected >= WPF; must be measured before any framework choice (ADR-0001). |
| Tests | none automated for interaction | 50-51 unit tests + injected-input harness | Keep ours. |

Nothing in Action Wheel contradicts a measured spike conclusion. It does add evidence for two ADR-0005 open items (allocation-free hook callback; liveness probe) and confirms that WinUI 3 transparency is a hack rather than a feature.

## 4. Possible reuse (not performed)
MIT allows reuse with attribution; none of this was copied. Candidates, each with the justification and the reason to hesitate:
1. **`ActionWheel.Core/RingGeometry.cs` `ClampOrigin` ordering** (bottom/right then top/left) - ~10 lines; our own `OverlayPlacement` already clamps at all corners and on a negative-coordinate monitor (spike unit tests); only the "pin top-left when oversize" tie-break is new. Re-derive, do not copy.
2. **Hook liveness probe** (`LauncherService.CheckHookHealth` idea) - concept only; our hook host would implement it on the hook thread with a keyboard-side probe as well.
3. **`Core/AtomicFile.cs`** - 50 lines; our product rules require the same pattern for outputs, so we will write one shared writer with tests (collision-safe naming is ours, not theirs). Concept only.
4. **`Build.ps1` `Invoke-Package` smoke-launch** - adopt the idea in our own build script (launch artefact, wait N s, assert alive, kill).
5. **`Verify-Bindings.ps1`** - only if we end up with XAML `{Binding}`; `x:Bind`/compiled bindings or a code-only UI make it unnecessary.
6. **`TransparentSystemBackdrop` + `DwmEnableBlurBehindWindow` recipe** - only as the starting point of a WinUI 3 overlay spike, never as product code without the spike proving Light theme, HDR (#8594) and the thin-border issue (#11172) are handled.

## 5. Open questions
1. Does a WinUI 3 (DirectComposition, `WS_EX_NOREDIRECTIONBITMAP`) window deliver OLE `DragEnter` over fully transparent pixels immediately, unlike our WPF layered window (spike §R-E)? Action Wheel cannot answer (no drops).
2. What is Action Wheel's cold first-open latency and idle working set? Not measured by them; needed before WinUI 3 is even a candidate in ADR-0001.
3. Does `AppWindow.Show(false)` make the `Activate()` + double-`Move` dance unnecessary? (Official API exists - feasibility doc §2.)
4. Is their hook liveness probe sufficient when only the keyboard hook died (trigger key = Space in our case)? Their probe is mouse-only.
5. Their flick geometry is relative to the press point; near edges the drawn ring and the gesture ring diverge. For an OLE drop the cursor is authoritative, so the ring must follow the cursor (spike §R-C). Which ring-shift rule do we adopt (shift ring vs shrink)? Still open in ADR-0004.
