# Threat model (V1 image conversion: PNG, JPEG, WebP, BMP, TIFF)

Scope: the resident host, the worker process and the files they touch. Everything runs locally as the interactive user. There is no network, no elevation and no telemetry.

## Assets
1. The user's source files. They must never be modified, moved or deleted.
2. Other files in the destination folder. They must never be overwritten.
3. The user's trust in a result: a file that looks like a successful conversion must be one.
4. The responsiveness of the desktop. The global hooks run in every input path.

## Entry points and trust boundaries
| Entry point | Untrusted input | Boundary / control |
|---|---|---|
| OLE drop on the overlay | Data object from any drag source; CF_HDROP path list | Only CF_HDROP is read, and only if the source allows COPY. The DROPFILES block is parsed in place within `GlobalSize`: a short header, an offset outside the block, an unterminated list, a path over 32,767 characters or a block over 64 MB is rejected as malformed. Before 2026-10-23, `DragQueryFileW` read out of bounds on such a block and crashed the host (ADR-0004 amendment). A failed read is retried from DragOver at most 20 times per drag, at least 100 ms apart, never in a blocking loop. One read slower than 200 ms, or 500 ms of reads in all, stops the retries, so a slow or hostile source cannot keep the UI thread busy. At most 10,000 paths are parsed and more than 1000 get no commands. Paths must pass `PathPolicy`: canonical (no trailing dots or spaces that Win32 would strip, which would name a different file), well-formed UTF-16, drive or UNC only (no verbatim `\\?\`, device `\\.\` or NT `\??\` paths). Explorer drops a file whose path exceeds 260 characters as its 8.3 short name. A path with an alias's shape is expanded with `GetLongPathNameW` on a task, never on the UI thread (a lookup through a symlink to an offline share took 21 s). Meanwhile the ring waits and a drop runs nothing; the expansion stops at 5 s or when the drag ends (checked between lookups), and if any path is left unexpanded the drag gets no commands. Paths refused for another reason are never looked up. Residual: a UNC path of alias shape is looked up on the network while the user hovers, before any drop. `PathPolicy` itself makes no file-system call: aliases are recognised by shape, because `Path.GetFullPath` looks up any name with `~` (a network round trip on UNC paths, on the UI thread, before 2026-10-24). The effect is COPY or NONE, never MOVE |
| File content | Any bytes under any name | The extension is a hint only. The worker checks the signature and enforces size limits (256 MB, 50 MP, 65,535 px per side; ADR-0015). Each worker can commit at most 1.5 GB (job object), and the pool never runs more workers than fit into the available memory. It checks the container structure: PNG chunks, CRCs, and IDAT inflating to the size IHDR implies; JPEG markers and scans through to EOI; WebP RIFF chunks; the BMP pixel array (RLE refused); TIFF strips and tiles (bounds, plus decompressed size for uncompressed, Deflate, PackBits and LZW). Any codec diagnostic on the worker's own stderr pipe counts as damage. Multi-page and animated inputs are refused. WebP payloads and JPEG/CCITT TIFF strips carry no checksum, so damage inside them can go undetected (residual). Decoding happens in a separate process |
| Image codecs (WIC, SkiaSharp/libwebp) | Parsers are a classic attack surface | WIC: Microsoft codecs only, created by CLSID (SEC-003); a test asserts the vendor. WebP: SkiaSharp's bundled libwebp (version tracked in the dependency matrix; CVE-2023-4863 class). Both run only in the worker, never in the host |
| Host ↔ worker pipe | Worker output after it has parsed hostile input | Lines are read through a bounded reader and refused as soon as they pass 65,536 characters; standard error is drained into a fixed buffer. Malformed or mismatched results are rejected. The host re-checks every success claim: the name must match the naming policy before any file is opened, and the file's format and SHA-256 must equal what the worker validated. There is a per-job timeout and kill; a kill-on-close job object ends any worker that outlives the host |
| Output path | Destination folder contents can change concurrently | The temp file is created exclusively (`CreateNew`) in the destination folder, then renamed to the first free name without overwriting. A folder that is, or sits inside, a symbolic link or junction is refused. Nothing is written outside the source's folder or the configured output folder |
| Settings file (`%APPDATA%\WinTools\settings.json`) | Hand-edited or corrupted JSON, written by the user or another program running as the user | Parsed with `System.Text.Json` into a fixed record. Every value is repaired to a safe default: trigger key from an allow-list (no modifiers), qualities clamped, an output folder that is not canonical and absolute falls back to the same folder. The worker re-validates the folder (canonical, existing, no link). A corrupt file is moved aside. A file whose schema field (any casing, number or string) is newer is never moved or overwritten, even when this version cannot parse it. Saving never throws: an unwritable path leaves the old file intact and the host running. A file over 64 KB is not read, moved or overwritten. No secrets are stored |
| Batch drops | Up to 1000 paths, possibly the same file twice or many with one stem | At most 4 workers; each file gets its own exclusive temp and no-overwrite name. A crash or hang fails only that file; a lane stops after 4 failures in a row, its first worker and 3 restarts (a success resets the count) and reports the rest as not run |
| Global input hooks | Every keystroke and mouse event on the desktop | The callbacks read three fields, swallow nothing, log nothing and allocate nothing. The trigger key can change at run time (settings) through one atomic field |
| Settings-changed signal (`Local\WinTools.SettingsChanged`, ADR-0016) | Any process of the same user session can set the named event | It carries no data: the host only re-reads its own settings file, with the same validation as at start-up. A process that can set the event can already edit that file |
| Settings window (`WinTools.Settings.exe`) | Its `--settings` argument, the settings file | Started by the host with an argument list (no shell) and the host's own settings path. It writes only through the atomic `SettingsStore`, and a file from a newer schema stays read-only. The folder picker's result is validated like a hand-edited value |
| "Start with Windows" (HKCU `Run` value `WinTools`) | A value another program may have written under that name | Written only when the user turns the option on: the quoted full path of this copy's host, no arguments. Deleted only if it points to this copy. Per user; no elevation, service or scheduled task |
| Tray menu | User clicks | "Open logs folder" starts `%WINDIR%\explorer.exe` with the host's own log folder as an argument (no shell, no file opened). Nothing produced from user files is ever opened |
| Folders in a drop (UX-009, ADR-0019) | Folder paths in CF_HDROP, named like files or not, links to folders | Names whose extension no kind claims are asked about (`GetFileAttributesW`, verbatim form) on the drop target's inspection task, never on the UI thread, with the short-name expansion's error mode and its single 5 s deadline. A folder is marked with a trailing separator; `PathPolicy` also checks the folder's own path, so a name that normalises to another folder or a device (`holiday \`, `nul\`) is refused, and any component named after a device is refused for files too. Roots are refused. A folder named like a file reaches the worker as a file and fails with `IsAFolder` |
| Text worker (`WinTools.Worker.Text.exe`, ADR-0020) | Any file or folder a user drops (File info, SHA-256) | A separate process like the image worker, in the same kill-on-close job, with the same pipe limits. It opens files for reading only (shared with writers) and writes nothing (Windows may update the last-access time, as for any reader); it parses nothing but a 4 KB signature header. Online-only files (cloud placeholders) are never opened, so nothing is downloaded. Links are followed to their target for the facts. A folder's own entries are counted, at most 10,000, with a 2 s deadline checked between entries. Its facts are believed only within `JobFacts`' bounds; a hash only as 64 lower-case hex digits. Copy path runs in the host and puts only the dropped paths on the clipboard |
| PDF worker (`WinTools.Worker.Pdf.exe`) and qpdf (ADR-0022) | Any file a user drops as a PDF: malformed objects, xref loops, decompression bombs, encrypted files | A separate process in the kill-on-close job; qpdf is its child, started with an argument list of fully qualified paths (never `-` or `@` first), a private environment, closed stdin, a 4-minute limit and a tree kill. The header must say PDF and the file must be local and at most 1 GB before qpdf reads it. A file that needs a password is refused, never guessed. Outputs are checked (opens, page count), zone-marked, and renamed without overwriting; the host re-checks name, header and SHA-256 (Split: a manifest of every page). qpdf renders nothing and runs no JavaScript; embedded files and links are never extracted or opened. Residual: `qpdf30.dll` imports WS2_32 through OpenSSL; not verified with a process monitor |
| Dialogs process (`WinTools.Dialogs.exe`, ADR-0019) | Its stdin request (ids and labels from the host), its stdout answer | Started with an argument-free `ProcessStartInfo` (no shell). It never receives file paths. Only an id the host offered counts as a choice; anything else, a missing or failed program, or 10 minutes without an answer, runs nothing, and a missing or failed program is reported. It joins the host's kill-on-close job and is ended 2 s after answering. Residual: whether it can take the keyboard after a drop is unproven (a background process cannot set the foreground); no module overflows a ring yet |
| Toast and info panel | File names from the drop, results from the worker | Text only, drawn by the host. File names are shown as names (no paths), and error codes are mapped to fixed sentences. The only worker text that reaches the user is facts (Image info), shown only from a believed success and believed only within `JobFacts`' bounds: at most 32, label up to 40 and value up to 200 characters, no control or bidirectional-formatting characters (ADR-0018). Neither window takes focus or accepts input other than a click that closes the panel |

## Codec-loading risk (SEC-003)
`CreateDecoderFromFilename`/`FromStream` would pick any registered WIC codec, including third-party ones installed by camera or RAW packs. That would run unknown parsers in our process. The worker never uses the auto-selecting factories. It creates the four built-in codecs by CLSID, and `CodecVendorTests` asserts that each one reports `GUID_VendorMicrosoft`.

## Residual risks (accepted for this slice)
- The worker runs with the user's full token. A restricted token or AppContainer is future hardening.
- If something other than the host kills the worker between writing the temp file and renaming it, a hidden `~wintools-<id>.tmp` can remain in the destination folder. It cannot be mistaken for a result.
- Codec diagnostics are captured by re-pointing the worker's standard error, including C runtime descriptor 2 in msvcrt.dll and ucrtbase.dll, at a pipe it owns. If a future codec reports damage some other way, the structural checks and full decode remain the defence.
- A folder named like an image (`x.png`) is offered a command and then fails with `SourceNotReadable`.
- Reading the source at conversion time hydrates a OneDrive placeholder. Capability resolution never reads files, so dragging alone never hydrates anything.
- A source deleted after it was read still produces its output, converted from the bytes the user dropped.
- Logs contain output file names, operation ids and error codes. They never contain file contents or full source paths. They stay under `%LOCALAPPDATA%\WinTools\logs`.
- UIPI: input to elevated windows is not seen by the hooks. This is documented, not worked around.
- Remove metadata keeps only an allow-list of elements and checks the result by walking the whole output (every byte must belong to an allowed element), but it is not a forensic anonymiser. Pixel content (faces, visible text), the file name and file-system timestamps are untouched, and unknown private data inside the pixel stream is not inspected.
- Memory (ADR-0015): images are limited to 50 MP, each worker to 1.5 GB of commit, and a batch never runs more workers than can all reach that cap within the commit the system has left, less 1 GB.
- **Found by the TASK 5 security review and accepted** (`docs/security/2026-10-21-hardening.md`):
  - A deliberately crafted PNG (invalid filter bytes with valid CRCs, or palette indices past the palette) or a BMP with palette indices past the palette still converts. The codec decides what those pixels become. Real damage to a PNG fails its CRC; a BMP has no checksum.
  - A worker killed by the timeout right after its final rename leaves a valid output while the batch reports a timeout for that file. This is the safe direction: a success is never claimed falsely.
  - The destination folder is checked for links by path and then written by path. A same-user process that swaps in a junction between the two could redirect the output; it can already write there directly.
  - Remove metadata keeps a colour profile byte for byte. Its description text can name a device.
  - A running batch cannot be cancelled from the interface (there is none in V1). A hostile batch costs at most the timeout per file; each file's work is bounded by its own size.
  - A JPEG whose only damage is a missing EOI marker is refused, like any truncated JPEG, although its pixels may be complete.
  - If a worker cannot be assigned to the host's job object, it runs without the memory cap and without kill-on-close. This is logged per batch (`job.done.jobObject`); on the supported Windows versions nested jobs make the assignment reliable.
