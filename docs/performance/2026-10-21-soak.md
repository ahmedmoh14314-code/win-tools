# Leak and stall soak runs (2026-10-21)

Machine: the development PC (Windows 11 Pro 26200, 16 GB, 12 logical processors, 120 DPI), in normal use: 4.6 GB of commit and about 2 GB of physical memory were available. Release build of `tests/WinTools.Soak` (local only, not CI). It drives the product's real overlay window and its real worker pool, and injects no input.

## Method
- **Samples:** after a forced GC, on one thread. Each records private bytes, GC heap, kernel handles, GDI and USER objects, and the thread count. There are about 40 samples per run.
- **What counts as a leak:** growth with the cycles. The median of the last quarter of the samples is compared with the median of the second quarter.
  - A one-off step (the runtime opening something on first use) or a single spike (the GC keeping memory it may reuse) moves neither median. A slope moves the last one.
  - New runtime threads bring their own handles; up to 8 per thread are not counted against the product.
- **Allowances:** GDI and USER objects 0, other handles 2, GC heap 0.5 MB, private bytes 2 MB.
- **The detector itself was checked:** with `--inject-leak` (one kernel handle and 4 KB per cycle), 2000 cycles reported handles +1051 and GC heap +4.2 MB, and a leak.
- Raw lines: `2026-10-21-soak-runs.jsonl`.

## Overlay: 10,000 show → paint → move → paint → hide cycles
After 250 warm-up cycles:

| | First sample | Last sample | Median growth, last vs second quarter |
|---|---|---|---|
| GDI objects | 7 | 7 | 0 |
| USER objects | 7 | 6 | −1 |
| Kernel handles | 271 | 277 | −1 (threads −3.5) |
| GC heap | 0.36 MB | 0.36 MB | 0 |
| Private bytes | 10.0 MB | 10.3 MB | +0.5 MB |

- Handles moved between 271 and 280 with the runtime's thread count and did not trend.
- Each full cycle took p50 6.4 ms, p95 8.4 ms, p99 11.8 ms, max 29 ms.
- **Budget "overlay show/hide leak: 0 growth over 1000 cycles": met, over 10,000.**

## Jobs: 3000 conversions through the worker pool
60 batches of 50 PNG → JPEG conversions, each batch with a new pool. 2 workers, as available commit allowed (ADR-0015).

| | First sample | Last sample | Median growth |
|---|---|---|---|
| Kernel handles | 294 | 297 | 0 |
| USER / GDI objects | 2 / 0 | 2 / 0 | 0 / 0 |
| Threads | 19 | 19 | 0 |
| GC heap | 0.55 MB | 0.58 MB | 0 |
| Private bytes | 12.0 MB | 15.2 MB | −1.6 MB |

- There were no failures, and no worker process remained.
- A batch of 50 took p50 291 ms, p95 349 ms.

**A measurement artefact found on the way:** an earlier run showed USER objects climbing from 2 to 6.
- Spawning the same worker 400 times from a plain Python process cost 0 USER objects.
- The cause was the sampling itself. It ran on whichever pool thread an `await` resumed on, and a thread's first user32 call (`GetGuiResources`) makes it a GUI thread.
- Sampling on one dedicated thread removed the growth.

## UI stall: overlay latency while every worker is busy
300 show + paint cycles idle, then 300 during a batch of forty 12 MP BMP → WebP conversions. The batch was still running when the last cycle was measured.

| Overlay show + paint | p50 | p95 | p99 | max |
|---|---|---|---|---|
| Idle | 8.8 ms | 11.8 ms | 12.4 ms | 14.3 ms |
| During the batch | 4.8 ms | 9.6 ms | 11.9 ms | 13.3 ms |

The work runs in other processes, so the overlay thread never waits for it. It is even a little faster during the batch, probably because the CPU clocks up under load. **Budget "UI thread stall during a job: 0 frames > 16 ms": met.** All 40 conversions succeeded.
