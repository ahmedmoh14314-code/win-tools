# V1 interface: Explorer runs and measurements (2026-10-21)

Machine: the development PC (Windows 11 Pro 26200, 120 DPI, one monitor 1920×1080, 12 logical processors). Release builds of `feat/v1-ui-polish` after the evaluator's fixes. The interface is described in `docs/design/ui-v1.md`, the decisions in ADR-0016.

## Explorer suite
The same 22 scenarios as at TASK 4 and the functional acceptance gate (`docs/performance/2026-10-21-hierarchical-menu.md`), each from its own shell, against the real Explorer. **71 of 71 cycles passed, every scenario on its first run.** Per-cycle records, without local paths, are in `2026-10-21-ui-runs.jsonl`.

The harness ran with **animations on** (`--animations on`, its new default). That is the heavier path: on this machine Windows' *Animation effects* is off, so "Follow Windows" would show no motion. It also checks more than before; no existing criterion was relaxed:
- Every producing cycle must show the result toast while Explorer is still the foreground window: 44 of 44 cycles.
- "Image info" must show the info panel with Explorer still in the foreground: 3 of 3. The harness then closes the panel with `WM_CLOSE`, as the old harness closed the message box.
- Every navigation sound the host logged follows the rules: one level sound per level change, never more ticks than sector changes. 71 of 71 cycles.
  - A full navigation (open a category, move to a command) gave 2 ticks and 1 level sound.

Fast releases, the screen corner, batches of 12 files with Unicode names, Escape and release outside the ring all passed with the same criteria as before. Sources were unchanged by hash, folders were clean, and no cycle left the button or Space down.

## Latency and memory (host log, all 22 runs)
| Metric | UI phase (p50 / p95 / max) | Functional V1 gate | Budget |
|---|---|---|---|
| Trigger → overlay shown, warm (n = 49) | 6.2 / 9.1 / 11.0 ms | 12.3 / 20.1 / 23.6 ms | ≤ 50 ms p95 |
| Trigger → overlay shown, first activation of a host (n = 22) | 10.9 / 13.7 / 14.8 ms | 33.6 / 45.7 / 60.5 ms | ≤ 120 ms |
| Trigger → first OLE DragEnter (n = 71) | 27.3 / 93.4 / 108.3 ms | 27.1 / 112.8 / 127.9 ms | — |
| Host private bytes at the end of a run | 11.2–19.5 MB | 9.4–16.0 MB | ≤ 100 MB |
| Host working set at the end of a run | 46.2–59.4 MB | 39.2–50.6 MB | ≤ 150 MB |

- **Faster to show.** The overlay is now shown with a layered window update instead of a synchronous `WM_PAINT`, its fonts are cached, and a frame is drawn off screen at start-up, so the first activation no longer pays for JIT compilation and font creation.
- **More memory.** Private bytes grew by about 2–3 MB: the fonts, GDI+, the rendering surfaces of three windows, the audio thread and the tray. It stays far inside the budget.

## Frames
- **Per session:** p50 29 frames, of which 24 come from the animation timer.
- **Slowest frame of a session:** p50 4.9 ms, p95 13.7 ms, max 18.1 ms (n = 71).
  - The one frame over 16 ms was in the first session of a freshly started host, with no job running.
  - No frame over 16 ms coincided with a job, which is the budget's definition ("0 frames > 16 ms attributable to job work").
- **Off-screen frame cost** (`tests/WinTools.Preview --bench`, 300 frames): p50 0.62 ms and p95 0.81 ms at 120 DPI.
  - The first version took 4.2 ms because it used GDI+'s gamma-corrected compositing; it was switched to the default after this measurement.

## Leaks: overlay soak
`tests/WinTools.Soak overlay`, 3000 show → paint → move → paint → hide cycles:
- GDI objects constant at 10, and USER objects at 9–10. Handles and threads did not grow; the GC heap stayed at 0.31 MB.
- No leak by the quarter-median rule.
- A cycle took p50 2.65 ms, p95 3.89 ms and max 13.6 ms. The functional V1 soak took p50 6.4 ms and p95 8.4 ms.

## Idle, start-up and settings reload
Measured with a local script that injects no input, with the PC untouched:
- **Idle CPU**, after 2 minutes, over 60 s: **0.000 %** of one core.
  - Private bytes 9.1–9.3 MB, working set 39.6–39.7 MB. Budgets: ≤ 0.1 %, ≤ 100 MB and ≤ 150 MB.
  - New since functional V1: the tray window, the sounds thread (it waits; started at launch to warm the audio path) and the settings-signal wait. None of them wakes while idle.
  - With the PC in use, the hooks thread does work for every system-wide input event. In 60 s of normal use it took 94 ms on this build and 172 ms on the functional V1 build; every other thread took 0 ms.
- **Process start to tray-ready**, five starts: 226, 236, 250, 333 and 337 ms (budget < 500 ms). The measurement runs from the launch to the `host.start` log event, which is written after the tray icon exists.
- **Settings reload:** after the settings file was saved and the signal raised, the host logged `settings.reload` (applied, trigger F9, sounds off, animations off) 225 ms and 289 ms later, in two runs. Most of that time is the PowerShell call used to raise the signal.

## Not measured here
- Mixed DPI and several monitors (one monitor at 120 DPI). The renderer is tested off screen at 96, 120, 144 and 192 DPI.
- Audio latency from a sector change to the tick reaching the speaker.
